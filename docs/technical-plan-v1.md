# 首期技术方案 v1（已确认）

日期：2026-10-09

依赖需求：[首期 spec](spec-v1.md)。用户已于 2026-10-09 确认需求及本技术方案，实现与验证记录见 README 和 docs/verification.md。

## 1. 推荐技术栈

| 层 | 方案 | 职责 |
| --- | --- | --- |
| 前端 | Vue 3 + TypeScript + Vite | 问答、会话和知识管理 |
| 业务后端 | Go + Gin | 登录、授权、上传、版本发布、会话持久化、SSE 代理 |
| RAG 服务/Worker | Python + FastAPI | 解析、切片、Embedding、检索、重排、生成和离线评测 |
| 数据存储 | PostgreSQL + pgvector | 业务元数据、知识切片、向量和任务 |
| 关键词检索 | rank_bm25 + 中文分词 | 在已发布知识快照内进行 BM25 检索 |
| 文件存储 | 本地持久化卷 | 保存原文件和不可变版本，后续可替换对象存储 |
| 模型 | qwen3.7-text-embedding + qwen3.7-text-rerank + deepseek-v4-pro | Embedding、重排序及生成的独立 API 适配器 |
| 部署 | Windows 原生进程；Docker Compose 可选 | 本机开发及可重复演示 |

与原 PRD 的差异：采用其轻量 PostgreSQL/pgvector 路线，统一业务与向量存储；首期不引入 Milvus、MySQL、Redis、Kubernetes 或完整 LangChain/LlamaIndex。RAG 各环节用显式接口编排，保留替换能力。

2026-10-09 环境补充：用户确认使用 Windows 本机 PostgreSQL + pgvector，未安装 Docker Desktop。原生部署使用项目目录内 PostgreSQL 16.15 + pgvector 0.8.6，默认本机 55433 端口；不注册系统服务，不改动已有 5432 服务，Compose 保留为可选方案。运行步骤见 [Windows 说明](windows.md)。

同日用户补充需支持云上部署。首期云部署采用 Linux 单机 Docker Compose，业务代码与 Windows 共用；数据库及原文件使用持久化卷，Go 与 RAG 共用 `/data/uploads`，外部通过宿主机 HTTPS 代理访问。Compose 补齐健康检查和进程退出后的自动重启，默认保持单个 Go 与 RAG 实例。跨机器、多副本需要对象存储与索引/会话并发协调，另行扩展。见 [云部署说明](cloud.md)。

BM25 为首期单 RAG 实例的内存索引，以 PostgreSQL 中不可变的已发布切片快照重建，适合当前演示范围。容量增加或需要多实例时再迁移关键词索引服务；此方案不宣称支持原 PRD 的生产级规模。

## 2. 服务边界

```text
浏览器 → Go 业务 API → Python RAG 服务 → 用户配置的模型 API
            ↓              ↓
         PostgreSQL + pgvector
            ↑              ↑
         文件卷 ← Python 导入 Worker
```

- 浏览器只访问 Go 公共 API；Python API、数据库和文件卷位于内部网络。
- Go 负责用户身份和知识范围确认；Python 不能依据未经业务后端验证的客户端身份决定访问范围。
- Python 返回结果和诊断事件，Go 负责保存用户会话与终态。
- 通过请求 ID、知识快照 ID、文档版本 ID 和策略版本贯通追踪。

## 3. 核心数据

- user：用户、口令哈希和普通/管理员角色；演示账号由本地配置创建，不开放注册。
- knowledge_base：适用组织、名称、当前发布版本编号。
- document：知识库、逻辑文档、标题、启用状态和当前有效文档版本。
- document_version：不可变原文件、内容校验值、来源、处理状态、模型及解析/切片版本。
- chunk：文档版本、标题路径、页码/章节、正文、内容校验值和向量。
- ingestion_job：版本、任务状态、重试次数、租约、进度和错误分类。
- chat_session/message：用户、知识库、消息顺序、改写问题、状态、知识快照和模型信息。
- citation_snapshot：引用编号、版本、切片、正文节选和定位信息。
- evaluation_run：数据版本、模型/参数版本、运行条件、聚合结果和逐样本结果位置。

Embedding 配置包含维度并在首次接入时校验返回值。先采用精确向量检索建立基线，按实测规模再启用适配维度的索引；不默认任意维度均可建立同一种近似索引。模型或维度改变需创建新索引版本并重新向量化，不能混用。

## 4. 导入与发布

1. Go 校验管理员权限、类型与大小，将文件写入随机 ID 路径，创建版本和任务；不执行原文件。
2. Worker 从 PostgreSQL 领取任务，使用租约与心跳保证重启后可恢复；处理结果幂等写入。
3. 文本 PDF 保留页码，DOCX/Markdown/TXT 保留标题或段落定位；不虚构非 PDF 页码。
4. 按标题和段落切片，过长段落再拆分。初始目标长度、重叠长度和分词策略配置化，用开发集调整。
5. 分批调用 Embedding API，遇到限流按服务提示退避；重试有上限。向量维度和数量不匹配即失败。
6. 新版本全部处理完成后，事务更新有效版本及知识库发布编号。
7. 查询绑定发布快照；BM25 索引按快照重建或切换，并且候选 ID 必须属于该快照。索引未就绪不能悄悄使用旧快照。
8. 停用更新发布编号，下一请求在两路检索中均排除该文档；旧会话引用读取其保存版本。

## 5. 问答链路

1. 校验会话归属，绑定知识快照；首次问题不改写，多轮问题使用有限历史进行指代消解。
2. 用同一查询分别执行向量与 BM25 检索，各取候选；使用 RRF 合并排名，避免直接相加不同量纲的原始分数。
3. 对候选做去重和重排，选取 Top-5 证据；Top-K 和上下文长度可配置。
4. 进行证据可回答性判定；重排分数只用于本次请求内排序，不直接套用跨请求统一阈值。根据所选证据是否包含必要事实、组织和条件进行结构化判定，并在开发集上校准判定规则。
5. 低证据分支返回拒答和终态，不输出编造答案；明显冲突则说明需要澄清的适用条件。
6. 高证据分支把切片作为不可信资料交给模型，以 [C1] 等固定证据编号约束事实性回答，流式转发答案。
7. 完成时校验引用编号及来源范围，保存引用快照。编号合法性校验不等同于事实支持校验；后者由离线评测及人工抽检完成。
8. 引用不合法或事实性回答缺少引用时发出校验失败终态，界面将已输出内容标为未验证，不计为成功答案。

### 重排序模型

用户已选择 qwen3.7-text-rerank。使用阿里原生 HTTP 重排接口；请求携带 input.query、input.documents 和 parameters.top_n，按响应 output.results 的 index 对齐候选 ID。官方说明 relevance_score 是当前请求内的相对分数。[重排接口](https://help.aliyun.com/zh/model-studio/text-rerank-api)

初始配置为融合候选 Top-20 重排后取 Top-5，候选数与上下文预算均配置化。记录重排前后排序、耗时和用量；故障返回明确错误，实验中不得无标记地跳过重排。

## 6. 公共接口与流式事件

- POST /api/v1/auth/login：登录。
- GET/POST /api/v1/knowledge-bases：知识库查询/管理员创建。
- GET/POST /api/v1/documents：列表/上传；新版本使用专门的版本上传接口。
- GET /api/v1/documents/{id}/versions/{version}/chunks：切片预览。
- PATCH /api/v1/documents/{id}/enabled：启停。
- POST /api/v1/ingestion-jobs/{id}/retry：失败任务重试。
- GET /api/v1/files/{version_id}：鉴权后读取来源文件。
- GET/POST /api/v1/sessions：历史列表/新建。
- GET /api/v1/sessions/{id}/messages：会话历史。
- POST /api/v1/chat：携带 session_id、question 和 request_id，返回 SSE。

SSE 按 status → evidence → answer_delta → citations → done 推送；拒答为 evidence → refusal → done，失败为 error 终态。evidence 包含判定和知识快照，不将非标定分数标成概率。done 返回消息 ID、耗时、Token 用量（提供商不可用时为 null）和 finish_reason。

Web 使用支持 POST 和鉴权的 fetch 流读取，不依赖仅 GET 的原生 EventSource。每条流携带 request_id 和序号；首次版本不支持断线续传，界面明确保留未完成状态并提供重试。服务器收到断开信号时取消上游请求，保存中断终态。

## 7. 模型配置与限制

- 分别配置 Embedding/LLM 的协议、服务地址、模型、凭据、超时与并发；两家接口使用独立适配器与配置。
- 凭据放在本地 .env，仓库只提交 .env.example；浏览器不持有模型 Key。
- 分别限制批量 Embedding、在线生成、离线评测的并发，避免评测占满问答调用额度。
- 记录实际 Token 用量；只有配置单价时才计算估算成本，缺失数据不能记为零。
- 首期不做答案缓存，以免知识版本替换后复用旧回答；可缓存按内容校验值和模型版本绑定的 Embedding。
- 模型超时是运行配置并通过实测调整；原 PRD 的 20 秒仅为初始交互候选，不能在未知 API 条件下承诺。

### 7.1 DeepSeek 接入

用户指定 deepseek-v4-pro，官方已列出该模型。采用 POST https://api.deepseek.com/chat/completions，Bearer 鉴权，stream=true 获取答案。[官方入口](https://api-docs.deepseek.com/)

建议问答默认显式设置 thinking.type=disabled，以减少答案正文前的等待；效果和延迟需实测。启用思考时，reasoning_content 与 content 分开处理，TTFT 只统计答案正文。[思考模式](https://api-docs.deepseek.com/guides/thinking_mode/)

流解析处理增量内容、finish_reason、最后内容块附带的 usage 以及 [DONE]；长度截断不计完整成功。结构化辅助任务可用 JSON Output，但仍校验候选编号、字段与截断结果。[接口协议](https://api-docs.deepseek.com/api/create-chat-completion/)

### 7.2 阿里 Embedding 接入

用户指定 qwen3.7-text-embedding。建议采用 DashScope 原生同步 HTTP 接口，显式设置 dimension=1024、output_type=dense；入库使用 text_type=document，查询使用 text_type=query。官方默认维度为 1024，单批最多 20 条；首期按短切片保守分批，不追求输入上限。[同步接口](https://help.aliyun.com/zh/model-studio/text-embedding-synchronous-api/)

用户已提供北京业务空间 API Host。本地配置保存带 https 的主机根地址；Embedding 使用其 /api/v1/services/embeddings/text-embedding/text-embedding 路径，重排使用 /api/v1/services/rerank/text-rerank/text-rerank 路径。适配器根据 text_index 对齐返回向量，并记录实际 usage；入库与查询保持相同模型、维度和预处理版本。

### 7.3 接入验证计划

- 配置齐备并进入编码阶段后，先用非敏感短文本验证两家 API 的实际可用性，不批量发送素材。
- 检查 Embedding 返回向量数量、索引、维度、数值有效性和批量错误；错误不能自动切换模型或维度。
- 检查 DeepSeek 的流式终态、Token 统计、超时与截断；区分空片段、答案正文及可能存在的思考字段。
- 检查重排返回索引是否越界或重复、结果数量与候选对应关系及业务错误响应。
- 文档核对不代表账号权限、额度或实际调用已经验证；当前未调用付费模型接口。

## 8. 验证与交付

- 单元验证：切片定位、融合排名、引用编号、会话归属、请求幂等和配置校验。
- 集成验证：真实数据库上的上传处理、版本原子切换、停用双路过滤、任务重试与中断持久化。
- 模型契约验证：按已确认协议验证流式事件、限流、超时、错误响应和向量维度。
- Web 走查：上传到回答与引用的完整链路，历史、版本替换、拒答、错误提示和管理员授权。
- 效果评测：冻结知识与测试集，真实 API 比较 BM25/向量/混合/混合加重排；报告失败类型和延迟。
- CI 默认执行无需模型凭据的验证；真实 API 全量评测手动触发并报告成本，后续有预算与稳定基线后再启用自动质量门禁。
- 首期 CLI 输出 JSON 与 Markdown 评测报告，无需先建设业务看板。

### 8.1 RAG 效果评测流程

评测先回答两个问题：检索是否找到完整证据，以及模型是否根据证据答对。执行链路与 Web 问答共用检索、重排、可回答性判定和生成组件，避免单独写一个更容易答对的评测版 RAG。

```text
导出素材并上传 → 冻结原文版本 → 构造与人工确认黄金集
                              ↓
                      开发集校准参数和拒答规则
                              ↓
                      冻结配置与最终测试集
                              ↓
               四组检索实验 → 端到端生成与引用记录
                              ↓
                程序指标 + 模型辅助评分 + 人工复核
                              ↓
                     对比报告与失败样本归因
                              ↓
                 在开发集改进 → 新配置回归最终集
```

先用 20 条开发样本打通全流程，最终准备至少 30 条独立开发样本和 200 条冻结测试样本。按事实主题分组拆分，避免同一事实的改写问句同时用于调参和验收。测试集只用于报告结果；若根据测试失败样本调整策略，须记录该轮接触并增加新的未见验收样本。

### 8.2 黄金样本与证据标注

模型可根据原文辅助提出问题和参考答案，随后由人工确认出处、必要事实和预期行为；未经确认的生成样本不能充当验收真值。多轮样本需包含原始追问、固定历史和期望指代目标。

| 字段 | 含义 |
| --- | --- |
| id、split、tags | 样本编号、开发/测试划分和场景分类 |
| case_revision、status | 样本修订号及草稿、待审核、有效、停用状态 |
| knowledge_base、corpus_version | 适用组织与冻结语料版本 |
| question、history | 问题及可重放的多轮上下文 |
| expected_behavior | answer、refuse 或 clarify |
| reference_answer、required_facts | 参考答案、必须覆盖的事实和禁止出现的错误结论 |
| evidence_groups | 每项必要事实的可接受证据；同组是等价来源，不同组是必须组合的证据 |
| source_version、locator、quote | 原文件版本、页码/章节/段落及经确认的原文节选 |
| change_reason、review_record | 修改原因、AI 建议及人工审核记录 |

证据锚点基于原文，不以当前切片 ID 作为唯一标准。数据准备模块将证据锚点映射到本轮切片：完整包含所需原文的切片或可合并覆盖的相邻切片才能记为覆盖；仅同一页或同一标题不足以命中。重复和重叠切片只覆盖同一证据组一次，避免通过增加重叠抬高召回。

### 8.3 对比实验

| 实验 | 检索路径 | 目的 |
| --- | --- | --- |
| A | BM25 → Top-5 | 关键词基线 |
| B | 向量 → Top-5 | 语义检索基线 |
| C | 两路各 Top-20 → RRF → Top-5 | 衡量融合效果 |
| D | 两路各 Top-20 → RRF Top-20 → Qwen 重排 → Top-5 | 衡量重排的增益与代价 |

所有实验使用同一原文、切片、问题改写结果、最终 Top-K、上下文预算及生成 Prompt。多轮改写独立测量后在检索对比中共享结果，避免把改写随机差异算作重排增益。正式端到端评测则重放完整多轮路径，并包含改写耗时与错误。

先跑全部四组的检索指标，再按所选实验进行端到端生成；完整验收对四组保存对应答案。在看测试结果前固定配置，用同一样本的成对差值比较，不挑选某次最好结果作为最终成绩。模型、切片与 Prompt 实验一次只变一个因素。

### 8.4 指标与评分实现

| 指标 | 实现 | 分母和解释 |
| --- | --- | --- |
| Recall@5 | 按证据锚点映射程序计算 | 可回答样本每题必要证据组覆盖率，再按题平均 |
| 完整证据覆盖率 | Top-5 覆盖全部必要证据组的题数 / 可回答题数 | 防止多文档问题只找到一半证据仍被认为解决 |
| MRR@5 | 程序计算首个相关证据的排名倒数 | 辅助衡量排序，不能替代完整证据覆盖率 |
| 答案正确率 | 固定业务评分规则，模型逐事实辅助判定并人工复核 | 所有可回答题；完整且无错误结论计通过，部分正确、错误拒答和请求失败均不通过 |
| Faithfulness | Ragas 将答案陈述与本次上下文做支持判断 | 完成生成且有可评估陈述的答案；无陈述、拒答、评分失败单独列出 |
| 引用有效率 | 程序校验引用 ID、文档版本、快照与定位 | 实际引用数；没引用的回答不能借零分母记 100%，另外统计应引用回答的覆盖率 |
| 引用支持率 | 逐事实陈述核对被引用证据，模型辅助与人工复核 | 被标注引用的事实性陈述；缺失引用另计 |
| 拒答与澄清正确率 | 按 expected_behavior 和拒答/澄清理由判定 | 无答案及冲突/适用范围题，分别报告；全部拒答会导致可回答题正确率下降 |
| 延迟与用量 | Trace 记录改写、检索、重排、判定、首内容和完成耗时 | API 错误、超时、截断率并列；在线和评测用量分别计量 |

Ragas 的 Faithfulness 衡量答案是否受上下文支持；AnswerCorrectness 是相对参考答案的事实与语义加权分数。后者可作辅助分析，但不能把平均 0.85 直接称为 85% 的业务答案正确率。[Faithfulness](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/faithfulness/)，[AnswerCorrectness](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/answer_correctness/)

实现使用轻量 Python runner：检索与状态指标自研，Faithfulness 接 Ragas 适配层，业务正确率使用可读的逐事实评分表。初始辅助评委使用现有 deepseek-v4-pro，独立评分 Prompt、非思考模式、固定低温度，不提供实验名称；它不能因答案来自同一模型而自行成为真值。

首轮正式验收人工复核 200 条测试样本在最终方案 D 下的回答，记录模型判定与人工判定的差异。后续复核全部变化/失败样本及不少于 40 条分层随机样本，保持人工覆盖率可见。报告分别展示自动评分与人工修订后的结果；失败评分记为待复核，未补齐评分前不宣称满足正确率验收。

CLI 测得的服务端首内容耗时与浏览器发送到渲染首字的用户 TTFT 分开命名和报告；页面指标另通过浏览器走查测量。流式加载提示、思考内容和空片段不能充当首字。

### 8.5 代码组织与运行模式

计划在 Python RAG 服务中设置以下模块；此处是实现设计，命令与模块尚待编码：

```text
rag/evaluation/
  dataset.py          样本校验、划分与证据锚点映射
  dataset_maintenance.py 文档差异、影响清单与修订草稿
  runner.py           执行实验与逐样本落盘、失败续跑
  retrieval_metrics.py 召回、完整覆盖与排名
  answer_judge.py     逐事实评分与拒答/澄清评分
  ragas_adapter.py    显式接入已配置的评委和 Embedding
  report.py           汇总、基线差值和失败归因
  cli.py              validate、run、compare、report 命令
```

评测入口区分 retrieval（不生成答案）、end-to-end（真实生成）、judge（复用保存答案评分）。Ragas 必须显式传入已配置的模型适配器，不能隐式使用其他提供商或未经配置的 Embedding。

首期提供 CLI 与 JSON/Markdown 报告，不新增看板页面。样本保存为本地 JSONL；报告输出 summary.json、cases.jsonl、comparison.md 和 failures.md。每题保存候选排名、最终证据、回答、引用、终态、评分依据与耗时，支持从某个 case ID 定位失败。

运行清单固定数据校验值、模型标识、生成/评分参数、Prompt/切片/评测规则版本和 Git commit。断点续跑只能补齐同一清单的缺失结果，不能混入新版本结果；计费调用前输出预期请求数，并限制并发、Token 预算和最长运行时间。

### 8.6 回归与失败分析

- 日常提交运行无外部费用的样本格式、程序指标和业务集成验证；20 条开发冒烟与 200 条真实 API 验收由手动触发。
- 先测检索，再测生成和评分，避免每次调整召回参数都生成并评判 800 个答案。更改 Prompt 时复用固定检索结果；更改模型/切片时重新生成对应阶段。
- 分析按解析丢失、切片边界、检索漏召回、重排降序、改写错误、错误拒答、生成漏事实、无依据陈述、引用错误和接口失败归类，并链接到原文及运行记录。
- 与上一固定基线比较同一批样本，输出每题得失与整体变化；出现模型波动时重复运行并报告范围，不只保存最好的一次。
- 新增数据或修改真值后重算基线，不能与旧数据集成绩直接比较。调优结论与最终验收样本保持版本记录。
- 自动门禁在基线稳定后启用：引用 ID 必须全部合法，业务正确率 ≥85%，Recall@5 ≥82%。回退容忍候选为正确率 0.5 个百分点、召回 2 个百分点，须经重复实验与人工确认后确定。

### 8.7 文档更新与评测集维护

评测集支持修改，但修改发生在新的草稿版本中。发布后的 dataset_version 绑定 corpus_version 和每题 case_revision，历史评测仍读取原来的语料、答案和样本，不能以新参考答案重写旧成绩。初始 200 条是覆盖规模目标，后续可扩展；删除或停用样本要说明原因并补足相应场景，不能因系统答错而移除困难题。

首期通过 JSONL 文件和评测 CLI 维护，支持导出草稿、人工编辑、AI 修订建议、校验、发布和版本差异报告。暂不增加评测管理 Web 页面。每次发布生成不可变清单和内容校验值，保留作者、审核记录、基于的语料及数据变更说明。

```text
文档新增、更新或停用
          ↓
原文段落差异 + 文档/证据到样本的依赖映射
          ↓
受影响题目清单 + 相关多轮/跨文档题 + 无答案/冲突检查
          ↓
AI 提出保持、重定位、修订、停用或新增建议
          ↓
程序核对出处与字段 → 人工审核原文及修改差异
          ↓
发布新语料对应的评测版本 → 重跑旧/新方案建立新基线
```

影响检测分成两部分：

- 确定依赖：按逻辑文档 ID、原文证据和多文档证据组寻找直接受影响样本。页码或切片变化但证据文本未变时，可重定位；规范化仅处理排版空白，不移除数字、单位、组织或适用条件。
- 扩展检查：对新增/变化段落进行问题相关性筛选，并检查同库无答案题、条件冲突题和共享前提。相似度只能筛选候选，不能保证发现所有影响；不确定变更进入人工清单，重要制度变更扩大复核范围。

| 文档变化 | 维护操作 | 主要成本 |
| --- | --- | --- |
| 排版、页码或证据位置变化，事实未变 | 重定位证据，程序校验，抽检 | 较低，以定位验证为主 |
| 流程、时限、金额、权限或适用条件变化 | 保留问题意图，修订必要事实和参考答案 | 与受影响题数及事实复杂度相关 |
| 新增知识 | 新题候选；原无答案题可能改为可回答 | 出题审核与负样本再检查 |
| 文档停用或知识删除 | 查找替代证据；没有替代时改为拒答/澄清或有理由停用 | 多文档依赖与预期行为复核 |
| 大范围制度重构 | 全面审核受影响主题并重建该部分样本 | 可能接近该主题首次建集成本 |

AI 使用已配置的 deepseek-v4-pro，以旧/新原文、变更段落及原样本为输入，输出结构化修订建议：case_id、action、修改字段、新证据位置、修改理由和待确认事项。AI 可批量草拟参考答案、必要事实、多轮问题与新场景；Ragas 也提供根据文档构造单跳/多跳测试候选的能力，首期维护优先复用已有样本与依赖映射。[测试集生成](https://docs.ragas.io/en/stable/concepts/test_data_generation/rag/)

参考答案必须依据新原文，不能把线上 RAG 的当前输出直接当作真值。程序核验所引段落确实存在、证据归属正确、编号和字段合法；事实含义、适用范围及冲突处理由人工确认。证据完全失效时先标为待审核，不自动当作通过或默默从分母移除。

成本分为维护与回归两项：维护通常集中在受影响题目，正式性能/效果回归仍要覆盖整个新测试集，因为新增文档可能改变未修改题目的检索排序。跨版本不能复用旧答案作为新语料的实际运行结果；评分缓存只在问题、参考答案、证据、生成答案及评分规则均不变时复用。

可按以下口径记录成本，不提前承诺节省比例或固定金额：

- 人工时间 = 影响清单审核 + 受影响题目审核 + 负样本/冲突题检查 + 抽检。
- API 费用 = 各模型实际输入/输出 Token × 对应单价，另计 Embedding 与重排用量；服务不提供用量时标为未知。
- 运行开销 = 差异/定位处理 + 新段落向量化 + 选定方案的回归 + 必要评分。

例如 200 条评测题中某文档关联 20 条题目，一次局部修改先处理这 20 条及相关负样本，而非重新编写全部 200 条。若修改扩大适用范围、解决原本无答案的问题或改变共享前提，影响集合会扩大；这个例子不代表必然只有 20 条需要审核。

文档新版本可按知识管理规则用于问答；若评测集尚未完成同步，则新语料的正式验收标为待更新，诊断报告注明数据不匹配。新评测版本发布后，在同一新语料/新测试集上同时运行旧配置与新配置，建立可比较的新基线；不把旧集合的 85% 与新集合的 90% 直接解释为提升 5 个百分点。

本节是首期新增的维护方案，随整体方案人工确认后实施。自动执行影响分析和生成修订草稿，正式评测版本由人工审核发布。
