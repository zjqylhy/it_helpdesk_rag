# 十七 IT 知识助手项目面试深度剖析

本章面向没有读过项目代码的开发者。先解释用户遇到什么问题，再说明系统为什么这样设计、具体如何处理，以及能保证到什么程度。原 R001–R200 编号和 P0/P1/P2 优先级保留，阅读顺序以本章排列为准。

实现核对日期：2026-10-15。本地代码基线为 `76c91ac`，效果实验工具的核心提交为 `021de0e`。文中“当前实现”是已有能力，“后续方案”是扩展设计；旧单库成绩和新跨库实验分别说明。

## 项目入门 先理解一次使用过程

这是一个根据已上传资料回答问题的网页应用。普通用户查 IT 操作方法，管理员上传和更新资料、分配阅读权限。项目不会因为模型知道某个答案，就跳过资料直接作答；也没有自动抓取全网或执行用户电脑操作的能力。

以“某校 VPN 怎么登录”为例：系统先检查用户能看哪些资料；学校没说清时先追问；范围确定后，既找相同关键词，也找含义接近的段落。它再从候选中挑最多五段，检查依据是否足够，最后生成带出处的答案。找不到资料时说明不能回答，而不是补编步骤。

资料分三层管理：知识库是按学校或用途组织的一组文档；文档有多个更新版本；每版再拆成较小的段落供搜索。只有新版全部处理成功，才开始用于新问题，失败则继续保留旧版。一次问题选定的版本清单叫“知识快照”，用来避免中途混用资料，它不是数据备份。

系统也区分资料版本与用户权限。资料更新后，旧回答可以保留当时出处；用户失去阅读权后，再看历史和下载来源仍要重新检查。已经发给用户或模型的文字则无法追溯收回。

## P0 必须掌握 核心设计与系统扩展

四十题。先讲清项目骨架与关键取舍，再准备规模、性能、质量及多实例演进；这些题决定面试官是否继续深入。

### 项目定位 架构与完整链路

#### R001 用 90 秒介绍这个项目

我做了一个 IT 知识助手：用户输入“VPN 怎么登录”“Windows 连不上网怎么办”，系统先从已上传的操作文档中找依据，再整理成回答，并标出原文出处。这是个人求职展示项目，目前没有企业客户或工单下降的业务数据。

系统分两部分：Go 管登录、文档、会话和权限；Python 管资料解析、搜索和模型调用。搜索同时使用“找相同关键词”和“找相近含义”两种方法，再重新排序，判断资料是否足够作答。资料不足时拒答，学校等条件不明确时先追问。

我重点解决了三个工程问题：新文档处理完才替换旧版；用户失去权限后，后续输出和历史资料也要受控；回答错误时能分清是没找到资料、选错资料，还是模型漏写。旧单库测试中，160 道可回答题有 144 道经人工判为正确；多文档题只有 22/30，因此后来补了错误分析和独立跨库实验工具。新 40 题已确定并保存，真实优化实验尚未运行。

#### R002 为什么做这个项目

我想验证自己能否把“调用模型生成文字”做成一个可以更新资料、管理权限、定位错误的应用。IT 操作资料有明确步骤和出处，也存在学校不同、版本不同就不能混用的情况，适合检验这些能力。

例如，两所学校的 VPN 文档都很像，系统仍不能把甲校账号规则给乙校用户。这里的业务需求是项目选定的场景，不代表已经访谈企业客户或证明节省了多少人力。

#### R003 项目面向哪些人 解决什么问题

普通用户用自然语言查找操作步骤，并查看依据；管理员负责上传、更新、停用文档和分配阅读权限；开发者通过一套事先确定答案标准的测试题分析错误。

因此，项目既要回答“怎么操作”，也要交代“依据哪份资料、适用什么学校、这个用户能不能看”。目前没有真实活跃人数、工单替代率或节省人时的正式统计。

#### R013 系统由哪些部分组成 各自负责什么

用户在浏览器页面输入问题，页面把请求交给 Go 后端。Go 先确认用户身份、会话和阅读权限，再调用内部 Python 服务。Python 找资料、调用模型，把回答一段段传回；Go 保存回答和出处，页面负责展示。

PostgreSQL 数据库同时保存用户、文档版本、聊天记录和可搜索的资料。原文件放在共享文件目录：Go 写入，Python 只读解析。Vite 用于本地前端开发，Nginx 在部署后提供页面并转发请求，它们不是另一套问答服务。

#### R049 用户提问后 系统完整做了哪些事

先由 Go 检查“是谁在问、会话是不是他的、允许查哪些资料”，并保存一条处理中记录。Python 随后确定本次使用的资料版本，结合最近对话补全问题，例如把“交大”接回“VPN 怎么登录”。

接着，用关键词和含义两种方式找候选段落，合并、重新排序，最多挑五段。模型先判断这些资料是否足以回答：条件不清就追问，资料不够就拒答，足够才组织答案。最后检查来源编号，保存回答和出处。

首次已选单库的典型成功请求要调用四次模型能力：问题向量、资料重排、充分性判断、答案生成；多库理解、追问改写、重试等还会增加调用。因此一个用户问题不等于一次付费模型请求。

#### R027 一份文档上传后 如何变成可搜索的资料

管理员上传文件后，Go 检查类型和大小，保存原文件，并在数据库创建“这个文档的新版本”和“待处理任务”。接口返回 202，意思是已接收任务，不是处理完成。

后台 Worker 取出任务，提取文字、拆成段落并生成向量。全部成功后，才在一次事务里保存段落、切换当前版本并记录发布清单。新问题此后才会用到新版；解析和模型请求不放在这段数据库事务里，以免长期占着锁。

#### R009 最值得展开讲哪三个技术难点

第一，更新资料时，保证一次回答使用一套确定版本，处理失败也不破坏旧资料。第二，权限变化后，不仅拦住新问题，还要处理正在输出的回答、历史记录和原文件下载。

第三，回答错了以后能定位原因：根本没找到资料、找到了却没选给模型，还是模型看到了仍漏写。它们需要不同的修复方法，不能统一归为“模型不够好”。

#### R007 这个项目相比简单问答演示多解决了什么

简单演示通常只展示“上传一份文档，然后能回答”。本项目还处理资料更新失败时继续使用旧版、后台任务中断后的恢复、权限撤销、历史回答的来源追溯，以及错误发生在哪个环节。

例如，新版还没处理完，用户不会搜到一半新、一半旧的资料；测试答错时，可以检查资料究竟有没有进入模型输入。面试时应拿这些具体机制说明价值，避免只用“企业级”概括。

### 主体组件与检索选型

#### R014 为什么把业务后端和知识处理分给 Go 与 Python

登录、权限、会话和文档管理是常规后端业务，我用熟悉的 Go 实现。文档解析、中文分词和评测有较成熟的 Python 工具，因此用 Python 处理知识问答部分。

这样能利用两种语言各自的开发便利，但也增加了内部接口、部署和排障成本。选择理由是职责与工具生态，并不是认为 Python 无法处理高并发；更小的项目完全可以统一用一种语言。

#### R016 为什么用 PostgreSQL 加 pgvector

PostgreSQL 保存业务数据；pgvector 是它的扩展，让同一个数据库也能保存和搜索向量。向量是代表文本含义的一组数字，用来寻找“措辞不同但意思接近”的资料。

合在一起后，新文档的段落、版本指针和发布记录可以在一次数据库事务中一起生效，减少两套存储之间的数据同步问题。当前只有数百段资料，使用精确搜索建立基线即可，还没有启用近似向量索引。[pgvector 官方说明](https://github.com/pgvector/pgvector)

#### R017 为什么没有使用 Milvus 等独立向量库

独立向量库能提供专门的向量检索能力，但同时要维护另一套服务，并解决“业务库里的版本和权限，是否与向量库一致”。当前资料量较小，先统一存储更容易验证。

以后若向量规模或查询量成为瓶颈，再用相同资料比较效果、查询耗时和运维成本。切换存储时，也要设计好新版资料何时对用户可见，不能只迁移向量就结束。

#### R018 为什么没有使用 Elasticsearch

项目当前在 Python 内存中对已发布资料做关键词搜索，使用 jieba 分词和 rank_bm25 评分，省去单独部署搜索服务的成本。

代价是每个 Python 实例都要加载资料、建立索引和计算得分。资料很多或筛选条件复杂时，可以考虑 Elasticsearch/OpenSearch，但当前内存方案不等于已经具备大型搜索集群的能力。

#### R019 为什么没有引入 Redis 和 Kafka

当前导入任务不多，直接把任务写进 PostgreSQL。后台程序从数据库领取任务；重复问答也通过数据库唯一约束拦住，所以暂时不需要再维护缓存或消息队列。

如果以后导入吞吐、多个消费者或消息回放需求增加，可以引入队列。但必须处理“数据库写成功、消息没发出去”等情况，常用方法是在业务事务里先记待发送事件，再补发；队列本身不会自动保证业务只执行一次。

#### R020 为什么没有用完整的 LangChain 或 LlamaIndex 编排

项目把“改写问题、搜索、排序、判断、生成”直接写成明确步骤，便于检查每一步用了什么权限、版本和模型调用次数。出了问题也比较容易定位。

代价是接口适配和异常处理要自行维护。评测的可选 Ragas 适配用了 langchain-openai，但这不代表用户问答的主流程由 LangChain 编排。

#### R021 Qwen 和 DeepSeek 分别承担什么工作

Qwen 提供两种能力：把文本转成向量，便于按含义搜索；对已经找到的候选资料重新排序。DeepSeek 则负责理解用户在问哪个学校、补全追问、判断资料够不够，以及生成最终答案。

项目也支持通过模型网关转发调用。网关里的 chat 等名称只是路由名称，背后的模型可能变化，因此历史成绩必须对应当时实际使用的模型，不能直接算作新模型的成绩。

#### R022 为什么要分别使用向量模型 排序模型和生成模型

三者承担不同工作。向量模型提前把每段资料转成数字，查询时可以快速找含义接近的段落；排序模型仔细比较问题与少量候选，挑出更相关的；生成模型把选出的资料组织成自然语言。

分开后可以独立分析效果和替换组件，但会增加调用次数、费用及等待时间。项目没有完成不同厂商的正式对比，不能说当前组合一定最好。

#### R025 目前架构最重要的取舍是什么

先减少组件，用一个数据库保存业务、向量和任务，并按单套服务运行来设计。这样比较容易部署、核对版本和复现故障，适合当前求职展示与开发阶段。

代价是资料规模扩大、服务多开和高可用方面的能力有限。面试时应说明何时需要演进，而不是把“组件少”直接等同于“可无限扩展”。

#### R024 为什么用 Docker Compose 而不是 Kubernetes

当前系统只运行一套 Go 服务、一套 Python 服务、数据库和网页服务。Docker Compose 可以把它们的启动关系、网络和数据目录一起描述，适合复现本地与单机部署。

Kubernetes 主要解决服务编排，不能替应用处理跨实例的任务归属、撤权通知或共享文件问题。先解决这些应用设计限制，再考虑更复杂的部署平台。

#### R052 为什么同时做关键词搜索和向量搜索

关键词搜索适合找“错误码 651”“某条命令”这样的精确表达；向量搜索先把文本含义表示成数字，适合把“电脑上不了网”匹配到“网络连接故障”。两条路径能互相补充。

但两种方法也可能一起漏掉复杂问题的一部分，所以还要检查每条路径找到了哪些必要依据。旧实验里，简单合并两路结果并未让所有指标都提高；进一步重排才带来主要实测增益。

#### R057 两路搜索结果如何合并 RRF 是什么

关键词分数和向量距离不能直接相加，所以项目使用 RRF，按“在各自列表中排第几”来合并。某段资料同时在两路靠前，就能积累更多分数；只在一路找到，也保留那一路的贡献。

公式是 score(d)=Σ 1/(60+rank_i(d))，rank 从 1 开始。实现按总分降序排列，并用段落 ID 处理并列。它解决的是两路排序尺度不同，不负责判断资料是否足以回答。

#### R061 重排模型解决什么问题

初次搜索为了尽量不漏资料，先取较多候选；重排再把问题和这些候选交给模型仔细比较，选出更相关的段落。可以理解为先广泛找，再精挑。

它找不回候选池里根本没有的资料，也不保证自动覆盖复杂问题的所有子任务。跨库重排还附上学校、库名和文档标题，帮助区分相似内容。

### 核心正确性与效果设计

#### R034 如何把文档拆成适合搜索的小段落

把整篇文档作为一个搜索单位太粗，模型也不需要每次看全文。因此系统先保留原文段落，再把过长段落按 700 个字符切开，相邻两段重复 120 个字符，减少关键内容恰好被切断的影响。

每段同时保存原文位置和字符范围。短段落不合并，当前也没有让模型判断语义边界，或自动沿完整句子切分。这里的长度单位是字符，不是模型计费使用的 token。

#### R044 新版文档何时开始用于回答

只有新版全部段落和向量准备好，才进入发布事务。事务会保存这些段落，把文档的“当前有效版本”指向新版，再保存一份当前可用文档版本的清单，最后把任务标为完成。

这些数据库修改一起提交或一起回滚，所以不会出现“版本已经切新，但段落只写了一半”。同一个知识库发布时会先加锁，避免两个发布同时计算清单而漏掉对方。事务失败，旧有效版本仍保留。

#### R075 一次跨库回答如何确定使用哪套资料

假设同时比较两所学校，系统要先确定本次使用甲校哪个发布版本、乙校哪个发布版本，之后不能边回答边改用刚更新的资料。这份成员版本清单就是本次的知识快照。

系统用一条 SQL 读取成员，并把库、版本、名称和组织等生成一个确定标识；用户权限筛选也会影响它。在线每个新问题可读取当时最新版本，离线正式测试则额外固定整套资料，不能混为一谈。

#### R087 为什么排序之后 还要判断资料够不够回答

“相关”不等于“能答”。例如问题要求完整安装流程，找到的段落可能只介绍软件下载地址，缺少账号和安装步骤。直接生成就可能补编缺失部分。

所以系统再让模型根据所选资料判断：够用就回答，缺资料就拒答，缺少会改变结论的条件就追问。这个判断也会出错，需单独统计错误拒答和错误放行，不能把它当成确定正确的规则引擎。

#### R117 为什么必须在搜索之前检查阅读权限

如果先从全库找资料、交给排序或生成模型，再在答案里删掉无权内容，受限正文已经发送出去了。前端不显示引用，也无法补救这次传输。

因此系统先查出用户能读的文档版本，再用它们建立关键词索引、执行向量搜索，并提供可见库信息。权限是输入边界，不是答案生成后的装饰步骤。

#### R120 权限撤销和回答正在输出时 如何协调

例如用户正在看某份受限资料的回答，管理员此时撤销了他的阅读权。当前单 Go 进程用读写锁协调：发送片段短暂拿读锁，修改权限拿写锁，提交变更后取消登记的旧请求。

等待模型时不一直持锁，否则撤权可能要等整个回答结束。保证范围是撤权生效后不再放行旧权限的后续片段，不能收回用户已经看过的内容。

#### R130 项目所说的 90% 正确率到底怎么算

旧单库测试共有 200 题，其中 160 题本来就应该能回答。人工核对最终答案，144 题正确，因此回答正确率是 144/160=90%。

另外 25 题应拒答、15 题应追问，分别有 25 和 13 题符合要求。这些是不同任务，不混进 160 的分母。新跨库流程尚无正式成绩，不能直接沿用这项 90%。

#### R068 为什么涉及多份文档的问题仍然容易答错

这类题要同时找全多处依据，再组合成完整步骤。旧 Windows 测试有八道失败：五道主要在初次搜索时漏了依据，两道是找到后在重排选择时丢掉，一道是资料齐全但答案漏写；部分题同时有多个问题。

八题交给模型的正文只有 802–1743 字符，都没有用完 8000 字符预算。因此不能把失败简单归为“输入太长被截断”，也不能只换更强的生成模型；应先修复最早漏证据的环节。

#### R151 答错后 怎样逐步确定问题出在哪里

沿资料经过的路径检查：原文是否在授权范围内，两路搜索是否找到，合并后是否还在，重排后有没有进入最终五段，以及答案有没有写出必要事实。

最早漏掉依据的环节作为主要原因，后面的问题可以同时记录。例如既没找到 USB 步骤，又漏写打印机检查，不能只修其中一处。历史没保存完整排序时，只能标信息缺失，不能猜出精确分数。

### 系统扩展 容量与演进

#### R194 突然有一千个用户同时提问 系统如何扩展

当前不能直接承诺承载。先测平均处理时间、每秒到达量和在途请求数量，再看等待、数据库连接、CPU、模型限额及慢请求。模型若处理不过来，单纯增加 Web 实例也没有用。

第一步应做有界排队和明确拒绝，避免请求无限堆积；再按瓶颈扩容。现有信号量只是限制部分调用同时进入，不是入口流量保护，也不能据它推算一千用户的容量。

#### R195 资料扩大到百万文档 应怎样改架构

先估算每份文档会拆多少段、生成多少向量，以及原文和索引占多少空间；“百万文档”本身还不足以判断容量。可能需要对象存储、批量后台导入、数据库分区或独立搜索服务，并提前构建索引。

同时设计好原文、业务版本和搜索索引何时一起对用户可见，以及撤权多久生效。搜索变快不代表更新与权限仍正确；这是扩展方案，当前还没有经过这个规模的验证。

#### R125 直接多开几个 Go 服务 权限设计还能照用吗

不能原样照用。数据库中的权限编号能被各实例看到，但读写锁和“取消哪些请求”的登记表只在各进程内。甲实例撤权，并不能靠本地锁与乙实例的发送动作严格协调。

另外，当前启动时会把全部生成中消息改为中断，也可能误伤其他实例。多实例前要重新设计请求归属、撤权通知和最终发送检查，再验证并发窗口；加一条消息广播不等于已经证明一致性。

#### R188 如果要用于真实业务 应优先补什么

先测清系统能承受多少请求，补好过载保护、连接复用、超时、模型真实版本记录、监控和回答保存确认。否则加机器之后仍可能重复生成、费用失真或“页面完成但历史没保存”。

再处理多实例的任务归属和撤权协调，把共享文件迁到对象存储，规划搜索索引分发、备份及迁移。当前没有完整监控平台、企业 SSO 或 Kubernetes，不能把其他项目能力直接算到这里。

#### R196 想让回答更快 应先优化哪里

先分别测理解问题、生成向量、数据库搜索、关键词打分、重排、判断和生成耗时，再看浏览器是否被代理缓冲。这样才知道用户等的是哪个环节，而不是凭感觉删步骤。

可针对瓶颈测试连接复用、有上限的跨库并行、跳过不必要的理解调用，或缓存安全的计算结果。减少检查、换快模型可能影响质量，要同时比较正确率、拒答和成本。

#### R197 如果希望正确率从 90% 提升到 95% 怎么做

先确认仍是同一种任务和分母，再把失败按场景及处理阶段拆开。只在开发题上选择一个改进变量，然后用未用于调参的测试题比较新旧结果，同时看误拒答、费用和速度。

不能删困难题、放宽事实要求或多跑几次只留最好答案。当前新跨库流程甚至还需先建立自己的真实基线，不能直接从旧单库 90% 出发宣称跨库提高到 95%。

#### R072 更换向量模型时 为什么不能直接继续使用旧向量

不同模型把文字映射到数字的规则可能不同，即使都输出 1024 个数，也不代表这些数字处在同一个可比较的空间。用新问题向量搜索旧资料向量，结果可能失真。

当前会检查配置中的模型名和维度，不一致则拒绝并要求重新导入。进一步扩展时，可后台生成一套新向量，比较效果后整体切换并保留旧版回退；还要核对网关实际模型，而不能只看别名没变。

#### R098 为什么没有答案缓存 以后加缓存要考虑什么

当前不缓存完整答案，主要避免资料更新或用户被撤权后继续命中旧回答。模型失败时也不会自动切另一个模型、联网补资料来凑答案。

以后若缓存，至少要把问题、用户可见范围、知识版本、模型和提示版本纳入缓存条件，并设计撤权后失效。不能只按问题文字缓存，否则同一句问题可能把有权限用户的答案给无权限用户。

#### R182 为什么备份数据库之外 还必须备份原文件

数据库里保存的是文档路径、版本和内容指纹，原文件在另一个目录。只恢复数据库，可能留下“有记录却找不到文件”的引用和下载。

因此应在尽量停止写入的同一窗口备份两者，恢复后比较表数据和文件指纹，再验证权限、历史、上传和问答。当前有本地 Docker 恢复记录，不代表已具备跨地域灾备或正式 RPO/RTO，也就是可接受丢多少数据、多久恢复的承诺。

#### R183 数据库结构升级 为什么不能永远放在服务启动时做

当前 Go 启动会执行增量建表和迁移，便于单实例部署。但多实例同时启动、表很大或迁移失败时，可能争锁、阻塞甚至让版本不兼容。

生产演进可把迁移独立执行：先新增兼容字段，让新旧程序都能运行，再回填数据，最后移除旧字段。这个分步方案是后续设计，不是当前已有完整迁移平台。

## P1 高频深挖 关键机制与工程难点

九十题。围绕 P0 的设计理由展开实现、约束和验证。Go 后端岗位优先会话、权限、事务及故障窗口；AI 应用岗位优先检索、跨库、评测及模型适配。

### 导入任务 版本与一致性

#### R028 为什么上传之后还要后台处理

解析大文档和调用向量模型可能较慢。如果始终占着上传连接，用户容易等待超时，服务重启后也不好判断处理到了哪里。

所以上传只接收文件和创建任务，后台再执行耗时操作。页面每四秒查询一次处理状态，展示等待、处理中、成功或失败；这不是后台已经完成时才返回的同步接口。

#### R032 项目能解析哪些内容 有哪些限制

PDF 读取可提取的文字并保存页码；DOCX 读取段落和标题；Markdown、TXT 读取 UTF-8 文本并保留段落或章节位置。这些位置用于展示出处和核对测试证据。

当前不支持扫描件 OCR，也没有完整处理图片、复杂版面、DOCX 表格或 PPT。文件上传成功，不代表其中所有信息都被正确提取。

#### R035 为什么每段资料要记录原文位置和字符范围

一是用户需要找到原文，二是测试要判断系统有没有找到完整依据。例如，某条操作说明被拆到两个相邻段落里，就要检查两段合起来是否覆盖了整条说明。

如果只记段落编号，调整切分方式后编号可能全变；只记页码又太宽泛。因此要同时记录文档版本、段落位置，以及原文从哪个字符到哪个字符。

#### R036 为什么段落长度选 700 重叠选 120

它们是当前配置的初始值，还没有通过独立实验确定为最优。段落太短会拆散完整步骤，太长会混入无关内容；重叠能缓解边界丢失，但也会增加存储和重复搜索结果。

合理的调整方法是固定测试题，在开发集上比较关键依据是否找全、答案是否完整、输入量和重复比例，再决定参数。

#### R038 批量生成向量时 如何避免资料与向量对应错位

每批最多发送 20 段。模型返回时带有输入序号，系统按照序号重新对齐，而不是假设返回顺序一定与发送顺序相同。

系统还检查序号是否重复或越界、向量数量是否齐全、维度是否正确，以及是否包含非法数字或全零向量。有问题就让该次处理失败，不补零后继续发布。

#### R039 搜索问题和文档正文的向量有什么关系

搜索时，会把用户问题也转成向量，再与资料向量比较。两者必须使用兼容的模型和处理方法，否则数字长度相同也可能无法比较含义。

直连接口区分“问题输入”和“文档输入”；网关使用自己的统一协议，不能假定支持厂商的每个专用参数。更换模型时需要重新确认兼容性，不能只检查维度没变。

#### R040 为什么生成向量时不一直开启数据库事务

外部模型请求可能等待很久。如果此时一直持有事务，就会长期占用数据库连接和锁，影响其他操作。

当前先在事务外解析和生成向量，全部准备好后再用一个较短事务发布。这样失败时旧版仍可用；代价是处理重试可能重新生成整份向量，尚未做到按批次断点恢复。

#### R041 后台程序如何领取待处理的导入任务

多个后台程序如果同时看见同一条待处理记录，可能重复执行。因此领取时，数据库先锁住一条可处理任务，并写上执行者、领取次数和有效期；已经被其他执行者锁住的任务会跳过。

具体 SQL 使用 `FOR UPDATE SKIP LOCKED`。它适合任务队列竞争，但不适合要求读到完整一致结果的普通查询。[PostgreSQL 说明](https://www.postgresql.org/docs/current/sql-select.html)

#### R042 怎样判断后台任务是否还活着 失败后怎样重试

任务领取后有 90 秒的有效期，执行者每 20 秒续一次，相当于定期报告“我还在处理”。如果不再续期，其他执行者就可以在过期后接手，避免任务永久卡住。

租约恢复最多领取三次；一般处理异常会直接标失败，并非所有异常都自动重试。管理员可以对失败任务重新排队，此时重置领取次数和进度。

#### R043 任务被接手后 原执行者恢复了怎么办

例如，旧执行者短暂卡住，新执行者已经接手，旧执行者随后又算出了结果。系统在发布前要锁任务记录，重新检查当前执行者是否仍是自己、任务是否在处理中、有效期是否未过。

检查不过就不能发布，防止旧结果覆盖接手者的工作。但已发给外部模型的请求可能仍会执行和计费；这个机制控制的是结果能否写入，不是撤销所有外部动作。

#### R045 同一知识库的两个文档同时更新 会丢掉其中一个吗

如果两次发布各自读取旧清单再覆盖，确实可能漏掉另一次更新。因此同一知识库的发布和启停操作，都先锁住知识库记录，轮流计算最新版本清单。

不同知识库仍可独立发布。跨库查询用一条 SQL 读取各库当时的版本，不代表所有库被强制发布成同一个统一版本号。

#### R047 停用文档和撤销用户阅读权限有什么区别

停用表示后续新问题不再搜索这份文档，但旧回答仍可以说明当时依据的是哪份资料。撤权表示某个用户现在不应该再看到来源，因此连历史回答和文件下载都要重新检查。

两者不能混用：普通资料下线不等于删除所有历史；保密权限撤销也不能仅靠让新搜索忽略文档来完成。

### 召回 融合 重排与上下文

#### R050 BM25 如何按关键词找到资料

BM25 是一种关键词评分方法：词在某段资料里出现得多，通常更相关；词在所有资料里到处都有，区分作用就小；还要考虑段落长短，避免长段落只因词多就占优。它擅长命令、型号、错误码和专名，对换一种说法的同义问题较弱。

常见形式是对查询词求和：IDF(t) × tf(t,d) × (k1+1) / [tf(t,d)+k1×(1-b+b×|d|/avgdl)]。tf 是出现次数，IDF 衡量词的区分度，|d| 和 avgdl 是当前及平均长度；k1 控制词频收益逐渐变小，b 控制长度影响。项目使用 rank_bm25 的实现，中文分词另由 jieba 完成。[组件说明](https://github.com/dorianbrown/rank_bm25)

#### R053 向量搜索怎样判断两段文字的含义是否接近

模型把文本转成固定长度的数字列表，系统比较问题与资料向量的方向差异。当前使用余弦距离，越小表示方向越接近；SQL 中对应 `embedding <=> query_vector`，距离相同再按段落 ID 排序。

距离不是“答案正确概率”。当前会做精确排序，还没有建立 HNSW、IVFFlat 等近似向量索引。

#### R054 为什么当前先做精确向量搜索

资料较少时，可以直接比较向量，先确认算法在不引入近似搜索误差的条件下能找到什么。以后再测试更快的近似索引，才知道速度提升是否牺牲了召回效果。

数据变多后，计算量与向量数量、维度有关，还要看权限筛选排除了多少内容。小库里搜索快，不能证明百万向量仍然快。

#### R055 如果要加速向量搜索 HNSW 和 IVFFlat 怎么选

这是后续方案。HNSW 把向量连接成多层邻近图，查询时沿图寻找相近项，通常查询表现较好，但建图和内存成本较大。IVFFlat 先把向量分组，查询时只搜部分组，需要权衡分组数量和搜索范围。

引入前要用实际资料和权限筛选条件比较：必要依据还能否找全、慢请求耗时、内存和建索引时间。项目目前没有实际启用这两种索引。

#### R058 为什么不直接相加关键词得分和向量得分

它们的单位和范围不同，直接相加可能让数值更大的一路主导结果。RRF 只使用排名，避免先人为调整两种原始分数的尺度。

代价是忽略了第一名与第二名究竟差多远。公式中的 60 是当前固定选择，还没有在本项目中比较多个取值来确定最优。

#### R059 A B C D 四组实验分别比较什么

A 只按关键词搜索，B 只按含义搜索；C 将两路各前 20 个结果按 RRF 合并，再取前五段；D 在 C 的候选基础上调用排序模型，再取五段。

这样可以分别观察语义搜索、融合和重排带来的变化。四组实验来自旧单库流程，当前跨库问答只支持 D，不能说新跨库也完成了同样四组对照。

#### R060 为什么合并两路结果有时反而变差

增加候选也会带来噪声。例如，问题需要同时说明 Wi-Fi 和打印机，排名靠前的五段却都在讲 Wi-Fi；这些段落可能都相关，但缺少另一半答案。

RRF 只融合排名，不知道必须覆盖哪些事实。因此混合搜索不是逐题都能提升的保证，需要保留退步题并分析原因。

#### R062 重排分数高 就表示可以放心回答吗

不表示。高分只是这次候选里相对更相关，并没有被标定成“有多大概率答对”。最相关的一段，也可能缺少必要前提或完整步骤。

所以项目还让模型判断选中的资料是否足够回答，而不是直接按 0.5 等分数阈值放行。设阈值需要用开发题验证误放行和误拒答。

#### R064 最多五段和 8000 字符限制的是什么

系统最多选五段资料，并限制这些段落正文的总字符数为 8000，防止把过多内容交给模型。单库选择时遇到装不下的段落就停止；跨库会跳过该段，再尝试较短内容。

这不是整个模型请求的长度上限，因为标题、学校名称、JSON 包装和指令也占输入空间；更不是 8000 token 的计费承诺。

#### R065 当前有没有对重复证据去重

同一段资料如果被两路搜索同时找到，会按段落 ID 合并。但两段 ID 不同、正文相同的资料，目前仍可能一起占用五个名额；系统只是记录这种情况，尚未自动去掉。

后续去重也要保留来源和权限：正文相同，不代表两份资料的适用组织、出处或可见用户相同。

#### R066 父子块 MMR 和相邻扩展分别能改善什么

这些是候选改进，当前没有实现。父子块是用小段定位，再给模型较大的相关上下文；相邻扩展是找到一段后补上前后内容；MMR 则在相关性与重复程度之间取舍，避免结果都讲同一件事。

它们都会改变输入量和证据分配，应该逐项对照测试，不能一次全加后无法判断哪项有效。

#### R070 如果关键资料根本没进入候选结果 怎么排查

先确认文件是否正确解析、资料是否在允许范围内、问题是否被改写错，再分别查看关键词和向量搜索的前 20 项。这样可以区分原文缺失、范围选错和搜索没命中。

确认原因后，再在开发题上尝试问题拆解、别名、搜索数量或切片调整。只改重排无法找回候选池之外的资料。

### 跨库 多轮与回答约束

#### R073 用户不选知识库时 系统搜索哪些资料

默认搜索管理员设为“纳入默认问答”的知识库，并且只使用该用户有权阅读的资料。显式选择知识库时，也仍然要过权限检查。

一次最多指定 32 个库，重复 ID 会合并，非法或不可访问的范围会报错。系统不能在用户选错库时悄悄改成搜索全部库，以免扩大范围。

#### R074 为什么把搜索范围保存在会话里

用户已经选择“只查交大”，后续说“账号呢”，通常仍是在问交大。把范围保存在会话中，可以保持这个上下文，Go 也不必相信浏览器每轮重新提交的范围。

页面切换范围会开启新会话，打开历史会话则恢复原范围。默认“全部业务库”仍会随管理员配置变化，不代表永远固定为会话创建时的那些文档版本。

#### R076 问 VPN 怎么登录 为什么可能先追问学校

不同学校的登录账号、域名和配置可能完全不同。问题没有交代学校时，系统不能因为某份文档更相似，就猜用户属于那所学校。

如果可搜索范围里有多个相关组织，就先询问学校；已经明确只查一个库时直接带入其组织，避免重复追问。能够答什么取决于资料和条件，而不是仅看搜索排名。

#### R077 用户只回复交大 系统如何继续回答

系统会读取最近有效的问答，把“交大”理解为对上一轮“VPN 怎么登录”的补充，形成“交大 VPN 怎么登录”这样的独立问题，再重新搜索。

聊天历史只用于理解指代，不作为事实依据。上轮助手即使说过某个操作，本轮仍应从当前允许访问的资料中找到支持，避免错误一轮轮传下去。

#### R078 为什么不把全部聊天历史都交给模型

历史太长会增加费用、噪声和旧错误的影响。当前只取最近最多四个已完成或待澄清的问答轮次，即最多八条用户/助手消息。

失败、中断或因为失去来源权限而隐藏的回答，不进入有效历史。当前没有长期记忆、用户画像或对话摘要机制。

#### R079 如果模型选错知识库 怎样防止越界

用于选择范围的模型只能看到用户允许访问的库信息，输出的库 ID 还要由程序检查是否都在白名单内；行为类型、问题格式和比较标记也必须符合要求。

不合法就报错，不能信任模型自行给出的新 ID，更不能失败后扩大成搜索全库。模型帮助理解意图，最终可访问范围由程序和数据库决定。

#### R081 跨库搜索如何避免大知识库占满结果

如果直接把所有段落放在一起排名，大库可能占据几乎全部候选。当前先在每个库分别搜索和融合，再轮流从各库拿候选，合计最多 40 项，最后统一重排。

这是为比较对象保留机会的取舍，也可能丢掉大库里更多相关段落。问题向量在多个库之间复用，但这种分配方式并没有被证明对所有资料分布都最优。

#### R082 比较两所学校 如何保证双方都有依据

系统会记住“这次必须覆盖哪些学校”。重排后，先为每个要求的库保留一段，再补齐其他资料；生成前检查输入是否覆盖双方，生成后检查回答是否实际引用双方来源。

每边有一段，并不代表每边所有必要事实都齐了，完整性还需要后续判断和评测。缺少对象时，系统不会直接输出一份看似完整的比较。

#### R088 拒答和追问条件分别用于什么情况

拒答表示当前允许搜索的资料不足，例如没有收录某校 VPN 说明；追问表示补充条件后可能回答，例如还不知道用户属于哪所学校。

两者不能互相替代：资料不存在时不断追问没有意义；条件已经明确时又重复问学校，也会影响使用体验。测试时分别定义问题应该进入哪一种行为。

#### R090 系统怎样要求模型只根据资料回答

系统指令要求：只使用本轮提供的资料，说明适用组织和条件，每个事实段落附上来源编号，并忽略资料里夹带的指令。问题和资料作为结构化数据发送，跨校比较要分别说明。

这些约束减少混用和编造，但模型仍可能被误导。指令不是权限系统，访问范围和编号合法性仍由程序检查。

#### R091 回答中的来源编号如何检查

系统给本次最多五段资料编号 C1、C2 等，模型用 `[C1]` 标出处。生成结束后，程序检查回答里至少有一个编号，且每个编号都指向本轮真实资料；比较题还检查是否引用了所有要求的库。

这只能证明“引用确实存在”，不能证明该来源支持旁边每一句话，也不能证明每个事实段落都附了引用。语义支持还需评测与人工核对。

### Go 会话 流式处理与权限

#### R099 会话编号和请求编号分别有什么用

session_id 标识一段会话，确定是谁的对话、使用什么范围；request_id 标识这段会话里一次逻辑提问，用于识别重复提交。数据库不允许相同会话中重复创建相同请求编号。

网络重试如果仍代表原来的那次提问，应复用编号；换一个编号会被视为新请求。每条消息另有自己的记录 ID，三者不能混为一谈。

#### R100 同一个请求提交两次 系统会重放旧答案吗

不会。当前数据库会拦住重复请求，并返回 409，提示用户刷新历史查看；同一会话已有回答在生成时，也会返回冲突。

这种幂等保护的目标是避免重复接纳和重复生成，不是自动重放历史流，也不是断点续传。面试时要明确已实现的是哪一种重复处理行为。

#### R101 如何防止一个会话同时生成两个回答

如果两个请求同时检查“现在没有生成”，它们可能都通过。因此项目不只做代码判断，而是在数据库建立部分唯一索引：同一会话只允许一条状态为 generating，即正在生成的记录。

两个请求竞争插入时，由数据库拒绝其中一个。当前插入错误统一返回 409，数据库故障和业务冲突尚未做更精细的错误分类。

#### R102 为什么用 POST 请求接收流式回答

用户要提交问题正文，并携带登录令牌，所以前端使用 POST fetch 发请求，再持续读取响应中的文字。响应按 SSE 格式区分进度、正文、引用和结束等事件。

浏览器原生 EventSource 通常按 URL 建立事件连接，不方便直接提交这份问题 JSON 和自定义鉴权头。SSE 是事件数据格式，不代表项目必须使用 EventSource。[SSE 说明](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)

#### R103 为什么没有改用 WebSocket

问答主要是用户提交一次问题，服务器持续向用户发送答案，单向的 HTTP 流已经够用。停止按钮通过取消当前请求实现，不必为此维护长期双向连接。

WebSocket 适合双方持续互发消息的场景，但也增加连接管理和协议设计成本。选择应根据交互需求，而不是认为它一定比 SSE 更先进。

#### R105 用户关闭页面后 如何保存已生成的内容

页面断开会取消原请求，服务端也会尝试取消上游模型调用。但如果继续用已经取消的请求上下文写数据库，保存动作也可能立即失败。

所以 Go 在收尾时新建独立、最多五秒的上下文，保存已收到的文字和中断状态。数据库仍可能故障，此时只记录消息 ID 便于排查；独立上下文提高保存机会，不是绝对成功保证。

#### R106 服务重启后 正在生成的消息如何恢复

旧进程已经无法继续输出，但数据库可能仍写着“生成中”，导致会话一直被占用。当前 Go 启动时把这些记录统一改为中断，让用户能够继续操作。

这建立在只运行一个 Go 实例的前提下。以后多开实例，不能让新实例启动时误改其他实例仍在处理的消息，需要记录执行者和有效期再判断。

#### R109 一次请求有多层超时 怎么理解

浏览器请求经过代理、Go、Python 和模型接口，每层都可能先停止等待。当前 Go 问答上下文和写响应超时都是 120 秒，Python 模型请求默认 120 秒；内部 HTTP 客户端为十分钟，Nginx 读取超时为 600 秒。

整条请求仍受更短的限制控制，不能因为代理允许十分钟，就说回答可以持续十分钟。相同的超时值还应为错误收尾和保存状态预留时间。

#### R111 页面收到完成事件 就代表回答已保存吗

当前不一定。Go 先把完成事件传给页面，再在函数收尾时保存消息；两步之间如果数据库写失败，用户可能已看见完整答案，但历史里没有正确保存终态。

如果产品要求“收到完成就一定已保存”，需要先可靠写入，再发最终确认，并支持凭请求编号查询恢复。当前没有这项更强保证。

#### R113 登录和令牌是怎样工作的

登录时用 bcrypt 核验密码；成功后生成随机字符串作为 Bearer token，浏览器每次请求带上它。数据库只保存令牌的 SHA256 哈希和十二小时过期时间，不保存可直接使用的原令牌。

每次鉴权还检查账号是否被禁用，退出时删除令牌。当前不是 JWT，也没有企业单点登录或完整刷新令牌体系。

#### R115 文档阅读权限如何分配

管理员可以阅读全部资料。普通用户能看两类文档：显式设为全员可读的，或授权给他所属用户组的；属于多个组时，阅读权取这些组授权的并集。

权限附着在逻辑文档上，作用于该文档的各版本。新文档默认只有管理员能读，直到分组授权；旧文档升级时按已确认规则保留全员可读。

#### R119 权限变更编号有什么用

系统有一个全局递增编号，每次修改授权时，权限数据、编号增加和审计一起提交。问答开始时记下当前编号，读取资料及向用户发送片段时再比较；变了，就不能继续按旧权限处理。

这种设计简单保守，但一次权限变化可能取消所有在途问答，即使其中有些并不受影响。它以部分可用性换取更清楚的控制边界。

#### R121 已经发给模型的资料 能在撤权后收回吗

不能。取消网络请求不等于提供商删除已收到的资料，也不保证立即停止计算。权限检查和之后的外部模型调用之间，也没有跨系统事务把两者变成一个不可分割动作。

所以要尽量少发必要资料，明确模型服务的数据边界，并准确说明撤权能阻止哪些后续访问，不能承诺所有已发生的传输都被撤销。

#### R122 用户被撤权后 历史答案如何处理

用户再次打开历史时，系统重新检查回答依赖的文档是否仍可读。只要必要依赖失权，就返回“来源权限已变更，回答已隐藏”，清空对外返回的出处和调试信息。

这叫重新限制访问，不是把数据库中的记录物理删除，也无法自动清除浏览器已经保存或用户已经看过的内容。

#### R128 文档里夹带忽略指令之类内容 会怎样

这属于提示注入：资料本应作为数据，却试图改变模型行为。系统指令明确要求忽略资料、历史和名称中的命令，程序还限制可选库、引用编号和调用范围。

当前模型不执行系统命令或任意工具，减少了执行风险，但仍可能被诱导错误回答。需要攻击样本验证，不能把一句“忽略文档指令”当成绝对隔离。

### 评测可信度与优化闭环

#### R010 哪些项目数字可以用于面试

旧单库测试使用 9 份真实文档、7 个知识库、649 个检索段落。200 道测试题中，160 道应回答、25 道应拒答、15 道应追问条件；最终方案分别为人工回答正确 144/160、拒答符合要求 25/25、追问符合要求 13/15，多文档题正确 22/30。

后来另建的 40 道跨库题尚未运行真实模型实验，不能沿用旧成绩。Docker 环境另有一份部署验证文档，合计 8 库、10 文档、721 段，这是另一套环境的数据量。

#### R131 四组实验的效果如何比较

在使用同一改写问题的检索实验中，A/B/C/D 的必要依据平均 Recall@5 为 78.65%/81.04%/81.35%/94.48%。完整问答实验的模型辅助正确率依次是 66.25%/73.75%/72.50%/90.00%。

只有 D 完成对应人工正式裁决，不能把其他组的辅助分数说成人工结果。单独测搜索和完整重放问答，也是两类不同运行，数据不能任意混用。

#### R133 Recall@5 具体在衡量什么

它检查最终前五段资料找到了多少必要依据。一题可能需要两个事实，例如账号规则和登录入口；每项事实可以有多个可接受原文来源，找到其中任一个就算该项命中。

先算每题命中了几项、占全部必要项多少，再对可回答题求平均。它不是“有任意相关资料的题数除以全部 200”，也不是最终答案正确率。

#### R135 同一条原文分散在两个切片里 怎么判命中

测试记录原文的版本、段落和字符范围。系统把最终选中切片的对应范围合并，只有连续覆盖了完整原文，才算找到这条依据。

相邻两段可以共同完成覆盖，重叠部分不会重复得分。只在同一页、同一标题下找到几个词，不算完整命中。

#### R136 为什么不能让模型生成测试题后直接判成绩

模型可能给出不准确的参考答案、漏掉条件或定位错原文；如果被测系统和评委又有相似偏差，就可能一起把错误当正确。

当前先生成候选，再由人工核对必要事实、原文出处和应回答还是应拒答，最后固定发布。审核了题目标准，不等于后来系统生成的答案已经被判正确。

#### R137 开发题和测试题怎样避免重复泄题

不能只随机拆问句，因为“VPN 用什么账号”和“登录账号怎么填”可能测试同一个事实。项目按事实主题区分开发与测试，减少同一事实换个说法出现在两边。

看过正式测试失败后再针对它优化，这套题就更适合作历史回归，不能继续当全新盲测。旧 200 题只有 140 个事实主题，多文档题也集中在 Windows，推广结论要考虑这些限制。

#### R140 为什么测试时还要固定资料和权限

只固定题目不够。同一个问题，如果文档更新了、学校名称改了或测试用户能看的范围变了，就已经不是同一实验。

所以发布测试集时，还固定原文、文档版本、知识库成员、默认范围、用户组和授权集合，并用哈希记录身份。运行时再检查这些条件，避免在旧版本名下悄悄换了考试材料。

#### R141 固定测试资料后 用户被撤权还能继续跑吗

不能为了复现旧成绩而绕过现在的权限。测试读取器仍使用与在线相同的授权检查，发现用户、组、版本或正文变化就停止。

固定资料是为了比较公平，不是给测试程序永久阅读证书。因此最好在独立数据库副本里准备稳定测试条件，同时保持权限规则真实执行。

#### R142 自动评委如何评分 有哪些局限

评委模型根据问题、参考事实和原文，逐项检查答案是否漏步骤、用错组织、出现禁止错误或行为不符，并给理由。正式答案正确率则必须等待对应可回答题完成人工裁决，否则保持为空。

当前代码还要注意：评委会返回“引用是否支持答案”的字段 citation_support，但最终辅助正确布尔值并没有单独把它作为硬条件。所以不能把辅助分数说成每条引用都已严格验收；评委也需要用人工结果校准。

#### R143 Ragas 在项目里有什么作用

Ragas 是可选评测工具，这里主要用来辅助判断“回答是否得到所给资料支持”，不参与用户提问时的必经流程。

它不保证问题答完整、学校选对或实际操作正确。评测还会增加模型调用和费用；工具执行失败要单列，不能假装没成本，也不能直接当成用户答案已判错。

#### R145 出错 未执行和缺少信息时怎样计分

已执行但故障的题不能从分母删掉，否则系统越容易失败，剩下的平均分反而可能越高。还没执行的题记 pending，并报告总数与执行数，不声称测试已经完成。

没拿到的模型用量、尚未人工裁决的正式分数记为空值，不补成零。旧报告在仍有未执行题时，会把主要完整质量指标留空，具体指标仍要按各自分母解释。

#### R146 中断后续跑 怎样避免偷偷改变实验条件

续跑前比较清单：题目、原文、代码版本、模型路由、提示和预算配置等必须一致；跨库测试还固定用户及权限范围。不一致就停止，不能把不同实验接在同一目录里。

旧单库允许重试故障题并保留执行记录；新跨库入口保留已经写下的终态，修故障后要另开运行。两套入口的重试规则并不完全相同。

#### R147 回答延迟应该从哪一刻开始计算

至少区分三项：用户发出问题到看见第一段文字、到完整回答结束，以及离线评委完成评分。Python 的第一段输出，还不包含全部浏览器网络和渲染时间。

历史报告中的 total_ms 要先确认统计边界，不能直接称为线上用户 P95。新的跨库评测明确把问答计时停在辅助评分之前；当前也没有高并发下的正式延迟承诺。

#### R150 如何用真实失败说明排查能力

旧题 windows-test-040 是一个例子：操作路径和省电选项都已交给模型，但答案只写了取消选项，漏掉设备管理器、属性、电源管理等路径，所以人工判错。说明搜索正确后，生成仍会漏必要事实。

同时，这道题的评分标准比问句要求更具体，也提示新题要让问句和必要事实对应。应保留原裁决并改进题目设计，不能事后放宽标准把成绩改高。

#### R154 为什么优先实验复合问题拆解

旧八道失败中，五道主要是初次搜索漏了资料。把“同时解决网络和打印机问题”拆成两个搜索重点，有机会分别找到缺失依据；只在已有五段里重新分配，找不回根本没搜到的内容。

这就是选择实验方向的依据，而不是为了把流程包装成 Agent。重复证据和排序也值得优化，但应另做实验，避免混在一起无法归因。

#### R155 查询拆解方案具体如何执行

实验策略名为 split-v1。系统只对识别为复合的问题尝试一次拆解，要求返回空数组或两个不同的原问题连续片段，每段最多 2000 字符，不能拿完整原问题冒充子任务。

搜索时保留原查询，并把完整问题和条件带到两个子查询中，仍只查原来允许的库。拆解格式错误就退回原查询，同时记录额外调用，不能让拆解扩大权限或悄悄改问题。

#### R157 比较拆解方案时 哪些条件必须一样

baseline 是不拆解的当前流程，split-v1 是增加拆解的实验流程。两者使用同一套题、资料、用户权限、模型、重排和生成指令，最终仍最多五段、8000 正文字符、40 个融合候选。

允许变化的是多查询带来的候选内容。不能同时换模型、扩大输入、改评分标准，再把所有提升归到拆解身上。

#### R160 为什么人工评审时要隐藏方案名称

如果评审人知道哪份答案是“新优化”，可能更容易认为它好。当前把同题两份答案随机放左右，先隐藏策略名，同时提供相同问题、原文和标准，判完再揭示对应关系。

这叫成对盲审，可统计改善、退步、两者都通过和都失败。它减少方案偏好，但不能自动消除标准模糊或只有一位评审人的局限。

### 模型适配 失败与资源控制

#### R026 Go 和 Python 之间如何确认身份与权限

浏览器不能直接决定自己的用户身份或阅读权限。Go 登录鉴权后，把用户标识交给内部 Python 接口；该接口还要求内部令牌，Python 再查询这个用户能读的文档版本。

用户选择哪些知识库，只是在请求检索范围，不代表获得了这些库的阅读权。当前还依赖内部网络隔离，没有服务间双向证书认证等更复杂方案。

#### R165 为什么把模型调用集中写在一个适配层

不同服务商的地址、请求格式、返回序号和流结束规则不同。如果每个业务步骤各写一套，很容易漏掉超时、用量或错误处理。

所以统一提供向量、重排、结构化判断和流生成接口，在这里处理鉴权、路由、格式校验与预算，也便于换成本地假模型测试。返回 JSON 能解析，仍不代表里面的库 ID 或来源编号正确。

#### R167 网关失败后 为什么不自动绕过它直连厂商

网关可能承担统一权限、计量和模型路由。自动直连会绕过这些约束，还可能改变资料被发送的目的地及实验条件。

所以启用网关后，失败就明确报错；直连与网关切换是显式配置动作。当前也没有应用内透明切厂商、熔断降级或负载均衡机制。

#### R169 模型请求失败时 哪些情况会重试

普通 JSON 请求遇到 429、502、503、504 时最多尝试三次，优先参考数值 Retry-After，最多等十秒，否则按指数间隔等待；网络异常和其他状态并非一律重试。

当前没有随机退避，也不完整支持日期形式的 Retry-After。流式答案不自动从头重发，因为已经输出一半再重放，可能重复文字和计费。

#### R170 项目怎样限制同时发出的模型请求

在线 Python 接口共享两个信号量，分别限制最多三个 LLM 调用、两个向量调用同时进入；超过的请求要等待。每次问答另建用量记录，避免把两个用户的 token 算在一起。

后台导入和离线评测有各自进程或模型对象，不受同一份全局计数统一控制，重排也没有独立信号量。所以这不是全系统总限流，更不是每秒请求数限制。

#### R171 HTTP 客户端是否一直复用

后台导入在服务生命周期内复用客户端；在线问答则每个请求新建一份模型客户端，结束后关闭，只共享信号量和关键词索引。

这样容易隔离用量，但跨请求连接复用有限，可能多出建连和 TLS 成本。以后可共享底层连接，同时保留每请求独立的统计上下文，需验证并发时不串数据。

#### R172 如何判断模型正常结束 并记录使用量

流里可能包含正文、结束原因和用量。项目只把正文 content 展示成答案，不把 reasoning_content 当答案；同时要求正常 stop 和结束标记，缺任一项就视为不完整。

用量常在末尾才返回，中途断开可能拿不到，必须保留未知。结构化判断也要完整结束，不能把被截断但恰好可解析的内容直接接受。

#### R173 温度设为零 为什么也不能保证每次相同

温度控制生成时的部分随机性，零温度不固定服务商模型权重、硬件和内部服务策略。即使输入不变，不同时间也可能得到不同答案。

因此要记录模型路由、输入资料、提示和运行条件，必要时重复测波动。本地 seed 主要固定实验顺序和盲审排列，不能保证外部模型字节级重复。

#### R174 使用固定网关别名 为什么仍存在复现盲点

今天 chat 可能指向模型甲，明天仍叫 chat，却改为模型乙；向量别名也可能映射到另一套数字空间。只记录别名，无法确认两次实验实际用了相同能力。

当前方案要求运行前核对网关实际路由和配置版本。更稳妥的后续设计是让程序自动校验真实模型身份，不能只凭名称相同就宣称完全可复现。

### 数据存储 部署与工程验证

#### R175 数据库中的主要对象怎样关联

一个知识库包含多个逻辑文档，每份文档可以有多个不可变版本，每个版本包含用于搜索的段落。文档的当前版本指针决定默认用哪版；发布快照保存某一时刻可用的版本集合，导入任务对应待处理版本。

聊天会话属于用户并保存搜索范围，消息保存每次问题、答案、状态和出处。用户组及文档授权关系另外保存，决定哪些资料能被读取。

#### R176 哪些并发规则交给数据库保证

例如，同一版本不能插入两个相同段序号，一个版本只对应一个导入任务，同一库不能重复同一个发布号；同一会话不能重复接纳同一请求，也不能同时有两条生成中消息。这些通过唯一约束实现。

但文件内容重复、文档严格先后顺序并不全部由约束保证。向量列也没有写死 1024 维，主要靠应用检查，所以不能把应用层校验说成数据库会自动拦住所有非法写入。

#### R178 Go 和 Python 怎样使用数据库连接

Go 使用连接池，最多十个连接，查询结束要及时释放。Python 当前每次读取会新建异步连接，没有使用连接池，并关闭自动准备语句的阈值行为。

Python 写法简单，但频繁建连可能有成本。是否需要改池，应该看实际连接数、等待和查询耗时，不能因为用了 async 就认为数据库开销自然很低。

#### R179 内存关键词搜索扩大规模后会卡在哪里

系统要把可读段落加载到内存，首次分词并建立 BM25 索引，查询时在进程内打分。资料越多，内存和 CPU 开销越大；同步分词与打分还可能阻塞 Python 事件循环。

当前数百段可先用这种方式，扩展时应测试首次建索引和权限变化后的重建，再考虑后台预构建、线程/进程隔离或独立搜索服务。

#### R180 Docker 部署怎样保存文件和限制访问入口

数据库和上传文件放在持久化命名卷里，重建容器时保留；Go 能写上传目录，Python 只读。Web 和数据库的主机映射默认只绑定本机回环，Go/Python 不直接发布主机端口。

这些设置支持当前单机演示与隔离，但不等于生产最小权限、数据库高可用或完整安全部署。删除卷仍可能删除数据，不能把容器可重建理解为数据天然有备份。

#### R184 怎样分层验证这个项目

单元测试检查切片、合并排序、编号和格式等局部逻辑；本地假模型加真实数据库检查跨服务行为；浏览器测试确认用户能登录、看流和打开引用；真实模型探测确认厂商协议确实可用。

最后才用固定资料与测试题、人工裁决检查特定范围内的回答质量。前几层通过，不代表最后一层一定高分，各层不能互相替代。

#### R185 为什么持续集成不默认调用真实模型

每次代码检查都调用真实模型，会受费用、密钥、网络和模型波动影响。当前 CI 用虚构素材和本地假模型，检查 Go、Python、前端构建、数据库联测及容器基本启动。

真实质量测试另外固定条件并确认预算。工作流文件写好了，不代表当前这次修改已经在远端执行过 CI，也不能把假模型测试当作真实效果。

### 关键故障窗口与改进顺序

#### R189 文档处理到一半 服务重启会怎样

新版尚未发布，旧版仍然提供问答。后台任务不再续期后可以重新领取；旧执行者若恢复，发布前仍要检查是否有处理权。

重新计算可能多花向量费用，文件丢失则不能靠任务恢复凭空找回。因此要同时检查任务状态、当前文档版本，以及数据库和文件是否持久化。

#### R190 用户正在依据旧版回答 管理员此时发布新版怎么办

本次问题开始时已经选定一套文档版本，继续按旧快照回答，避免中途混入新版。之后的新问题再读取新版；历史引用保留当时版本和节选。

这是普通知识更新的语义。如果变化是保密权限撤销，就应另用权限变更机制停止后续输出，不能把“允许旧版完成”套用到撤权。

#### R191 回答输出一半 模型连接断了怎么办

保留已有文字，但把状态标成错误或中断，不伪造正常完成。Go 会用独立的短上下文尝试保存，用户可以查历史后重新发起请求。

系统不会自动重放整个模型流，避免重复内容和费用。中断时也可能拿不到最终用量，这部分成本应保持未知，而不是记零。

#### R192 撤权和最后一段输出同时发生 能保证什么

在当前单 Go 进程中，发送用读锁、权限修改用写锁，决定两件事的先后：撤权生效前已经放行的文字不能收回，生效后旧权限请求不能再放行片段。

数据库保存和浏览器实际接收仍各自可能失败。多实例时本地锁协调不到其他进程，必须重新设计并验证，不能直接沿用单进程结论。

#### R193 用户收到完整答案 但数据库保存失败怎么办

当前确实存在这个窗口，因为完成事件先传出，函数结束时才保存终态。需要根据消息编号查看保存错误，并区分“展示完成”和“保存成功”。

后续可改成先保存，再发最终确认，并让客户端凭请求编号查询状态。模型服务和数据库之间没有共同事务，不能简单宣称全流程绝对只执行一次且必定落库。

#### R200 如果重做一遍 会先调整什么

先把实际模型版本、问答与评分的独立费用、各阶段耗时，以及“答案已发出还是已保存”的边界记录清楚。这样才能可靠比较效果，并知道出了故障如何恢复。

然后完成独立跨库开发实验，决定拆解是否值得保留，再按实测优化连接、索引和多实例。旧固定报告与失败结果继续保留，避免每改一次方案就失去原来的比较基准。

七十题。掌握核心设计后按暴露出的知识缺口补充；文件格式、具体字段和协议边界不必抢在整体方案前介绍。

### 项目表达与局部选型

#### R004 为什么不用普通搜索或直接问大模型

普通搜索往往只返回链接或段落，用户还要自己找步骤、拼答案。直接问模型，则不能保证它知道项目里的资料，也不能保证它使用了正确学校和版本的规则。

项目先搜索资料，再让模型根据搜索结果组织回答，这种做法叫 RAG。它方便更新知识和展示出处，但仍可能找错资料、漏掉步骤或误判不能回答，并不会自动消除错误。

#### R005 为什么不先训练或微调模型

项目首先需要解决的是“从最新、允许用户阅读的文档中找依据”。把事实训练进模型后，更新某份资料、撤销某个人的阅读权限，都会更难处理。

所以先用检索来提供知识。以后如果有足够且稳定的标注数据，可以再测试微调是否改善任务理解或回答风格；当前项目没有做模型训练。

#### R006 为什么不把全部文档直接交给模型

资料很少时，全文输入可以作为对照方案。但资料增加后，每次都发送全文会增加费用和等待时间，也容易混入不相关学校的内容。输入足够长，也不代表模型一定能找到所有关键步骤。

当前做法是先限制用户可读的范围，再最多选择五段资料给模型。本项目还没有完成“全文输入与检索输入”的正式对照，不能声称检索在任何场景都更好。

#### R008 如何说明自己在项目中的贡献

按实际工作说明自己决定了什么：为什么分成 Go 和 Python、如何管理文档版本、如何控制权限、如何设计测试，以及发现错误后怎样选择改进方向。代码由 AI 辅助生成的部分，也应如实说明。

关键是能解释选择的理由、代价和验证结果，而不只是背出组件名称。个人开发时长、团队分工等没有提供依据的信息，需要本人补充。

#### R011 资料规模不大 为什么仍值得做

649 个段落不能证明系统能处理海量数据，但已经能暴露版本混用、学校混淆、权限变化和多段资料组合的问题。小规模也便于逐条核对错误，验证设计是否成立。

因此，项目价值主要是应用正确性和验证方法。数据扩大后的速度、容量和稳定性，需要另外测量，不能从这套小库直接推算。

#### R012 项目目前部署到了什么程度

Windows 原生环境和本地 Docker 已有实际运行、数据持久化等验证。仓库中的云部署记录只证明服务器基础环境、镜像和备份准备，不代表应用迁移、实际启动及 HTTPS 已完成验收。

面试时要分别说清“能够在本地运行”“准备了云部署方案”和“已经通过云端验收”。旧部署记录不能证明服务器现在仍在正常运行。

#### R015 为什么选择 Gin 和 FastAPI

Gin 提供 Go 业务接口所需的路由、中间件和响应能力；数据库操作直接用 pgx，便于明确写出事务和 SQL。FastAPI 则便于定义 Python 内部接口，并用 Pydantic 检查请求字段。

这些工具能满足当前开发需求，但项目没有做框架之间的同负载性能对比，所以不能把选择说成经过实验证明的最快方案。

#### R023 为什么前端使用 Vue 3

页面主要展示问答、聊天历史、文档版本和权限设置，Vue 3 加 TypeScript 已能满足需求。更重要的是正确展示逐步到达的回答，以及处理中、失败和未验证等状态。

目前没有复杂的前端权限体系或完整 Markdown 富文本渲染。界面能显示内容，也不能替代后端真正的访问控制。

### 文件处理与检索实现细节

#### R029 如何避免上传文件覆盖服务器上的其他文件

保存路径不直接使用用户给出的文件名，而是用随机版本编号加允许的后缀生成，并以“文件不存在时才创建”的方式写入。上传文件最大 20 MiB，请求整体也有限制，失败时尽量删除本次文件。

只检查后缀不能证明文件内容安全，所以后续还要由对应解析器检查；当前并不是完整的恶意文件隔离系统。

#### R030 保存原文件和写数据库 能否一起成功或一起失败

不能直接做到。文件在磁盘上，文档记录在数据库中，两者没有共享事务。当前先写文件，数据库操作失败时再删除文件；但进程恰好在两步之间崩溃，仍可能留下没有数据库记录的文件。

以后可以增加临时存储区和定期清理，核对哪些文件还被版本记录引用。当前没有完整的孤儿文件清理机制。

#### R031 系统如何发现重复上传的文件

系统对原文件计算 SHA256，可以理解为文件内容的校验指纹；如果同一知识库已存在相同指纹，就返回 409 提醒用户，用户确认后仍可以继续上传。

这是操作提醒，并不是数据库强制禁止重复的规则，所以并发上传仍可能产生重复。它也无法识别“换了文件格式，但文字意思相同”的资料。

#### R033 如何处理加密 PDF 和异常压缩文件

加密 PDF 直接拒绝。DOCX 本质上是压缩包，系统先检查其中声明的解压后总大小，超过 100 MiB 就拒绝；提取文字过少时提示扫描件可能需要 OCR。

这些是基础限制，还不能替代解析进程隔离、CPU/内存限额或恶意文件扫描等措施。

#### R037 为什么按字符切分 而不按 token 切分

字符位置便于对应原文和引用，也方便测试核对。token 是模型内部处理文本的单位，中文、英文和符号的对应关系不同，所以 700 字符不等于 700 token。

以后可以在保留原文位置的基础上增加 token 预算和句子边界控制。当前 8000 字符的限制也只针对选中资料正文，不能当成整个模型请求的 token 上限。

#### R046 旧版本处理得慢 会不会覆盖较早完成的新版本

系统切换当前版本时，会比较文档版本的创建时间；通常情况下，后创建的新版本已经生效，早创建的旧任务就不能再覆盖它。

这还不是完整的严格顺序协议。如果要处理创建时间相同等边界，可以增加单调递增版本号；当前不能声称已经实现这种更强保证。

#### R048 新版失败 文件损坏和服务重启时分别怎样处理

新版处理失败，不切换当前版本，继续保留旧资料。后台读取原文件前会重算内容指纹，发现文件变了就失败。服务重启后，导入任务可在有效期过后重新领取；未完成的聊天会标为中断。

这些恢复都依赖数据库和原文件仍然存在，不能据此承诺磁盘损坏、数据库丢失时也能零损失恢复。

#### R051 中文资料如何分词 有什么不足

关键词搜索需要先把连续中文拆成词。当前用 jieba 分词，再把字母转小写、去掉空白，没有额外维护 IT 词典、停用词或同义词库。

VPN 名称、命令参数和学校简称可能因此被拆得不合适。排查关键词没命中时，要看实际分出的词，而不能认为使用了分词组件就一定正确。

#### R056 1024 维向量意味着什么资源成本

1024 维表示每段文字对应 1024 个数。按每个单精度数四字节计算，一条向量的数值约占 4096 字节；649 条约 2.54 MiB，一百万条约 3.81 GiB，还没算数据库行和索引等开销。

维度更高不代表回答一定更好。当前维度是配置选择，尚未做不同维度的独立效果对照。

#### R063 重排接口返回异常时怎样处理

接口会返回候选序号和分数，系统据此找到对应原文。序号重复、越界、分数非法或数量不足，都可能让资料与排序结果错位，因此会明确报错。

不能接口出错后悄悄跳过重排，却仍把成绩记作 D 方案。旧单库只请求前五项，跨库请求全部候选排序，因此历史可观察到的排序信息也不同。

#### R067 为什么提供原文时还要给标题和章节

短段落可能只写“取消这个选项”，不看它属于哪个操作流程，就不知道应该在哪里操作。标题和章节给段落补充背景，跨库时再补学校或组织信息。

当前生成答案时会带这些信息，但关键词索引仍主要处理段落正文，没有实现标题加权搜索。不能把“给模型看了标题”说成搜索算法也给标题加了权。

#### R069 资料找全率和答案正确率为什么不一致

找到全部指定原文，模型仍可能漏写；没有命中测试指定的原句，也可能找到另一种等价表述并答对。因此两个指标观察的是不同环节。

在旧 30 道多文档题中，初次候选和融合结果完整覆盖依据的各为 25/30，最终输入覆盖为 20/30，人工判答案正确为 22/30。不能拿其中一个数替代另一个数。

#### R071 搜索返回五段 就证明资料相关吗

不证明。当前关键词搜索没有用阈值先删除低分段落，向量搜索也只是返回相对最近的资料；即使全库没有答案，仍可能选出“最接近”的几段。

所以需要独立判断资料够不够，并测试无答案时能否合理拒答。想增加阈值，要先验证不会把困难但能回答的问题一起过滤掉。

### 跨库及生成的特殊边界

#### R080 用户问了没有收录的学校怎么办

如果明确学校无法匹配允许范围内的资料，就说明没有对应内容，不能用另一所学校替代。比较多个学校时，也不能只拿到其中一个的依据就假装完成比较。

已选单库时会跳过部分选库判断，但仍要在后续检查资料是否支持问题，不能把这个快捷路径理解为所有组织错误都已被排除。

#### R083 为什么一次最多比较五个知识库

最终最多给模型五段资料。要保证每个比较对象至少有一段依据，就不能同时比较超过五个库，所以系统会要求用户缩小范围。

“最多指定 32 个检索库”和“最多比较五个对象”是两个限制：一个控制查询范围，一个控制本次答案的证据分配。

#### R084 用户中途换学校或提到年份 怎么处理

本轮明确说的新学校、年份或条件，应优先于历史推断；这些条件会影响结论而又不明确时，需要追问。

文档上传时间不等于制度生效时间，历史资料也不代表现行规则。当前主要靠组织元数据和模型判断，没有独立维护制度有效期的知识系统。

#### R085 怎样验证多轮对话真的有效

一种测试直接给定历史，检查当前追问能否被正确理解；另一种让问题真实经过 Go 会话接口，检查前轮结果是否保存、哪些历史会被过滤，以及撤权后能否继续。

前者更容易固定条件，但不能替代完整会话测试。当前新 40 题的多轮部分主要使用固定历史，不能直接当作真实用户整段对话成功率。

#### R086 跨库搜索现在是否同时执行

当前查询向量和各库搜索主要按顺序执行，并没有把所有库操作一次并发启动。多个库共用同一个问题向量能减少模型调用，但库越多，数据库和内存处理仍会增加。

以后可以做有上限的并行搜索，同时验证数据库连接是否够用、取消是否能传播，以及模型接口是否被限流；不是并发开得越多越好。

#### R089 充分性判断给出来源编号 就证明判断正确吗

程序只会检查返回的是允许的行为、理由字段格式正确、来源编号属于本次资料，且选择回答时至少指定了依据。

这些检查能拦住格式错误和不存在的编号，却不能证明所有必要事实真的齐全。因此“接口结果符合格式”和“语义判断可靠”必须分别验证。

#### R092 没有引用 编造引用或回答被截断会怎样

没有来源编号、编号不属于本次资料，都会让最终检查失败。模型流还必须报告正常结束，并发送流结束标记；因长度限制等原因停止，不算完整成功。

用户可能已经看到部分文字，此时页面和历史将其标为未验证、错误或中断，不能只因接口返回 200 或已经有文字就算答题成功。

#### R093 为什么等整段回答结束后才检查引用

只有拿到完整答案，才能检查最终编号以及比较对象有没有被覆盖。先逐步展示文字，可以减少用户等待，但也意味着检查失败前，用户可能已看到不可靠内容。

另一种设计是先完整生成并验证，再展示；也可以逐段验证，但会增加等待或处理复杂度。当前没有逐段检查事实支持关系。

#### R094 为什么保存引用正文 而不只存文件链接

回答完成后，原文可能更新或停用。如果只存链接，用户将来打开时可能看到另一版内容，就无法解释当时为什么这样回答。

因此系统保存当时的文档版本、段落、节选和定位信息，称为引用快照。它用于追溯历史依据，但用户下载原文件或查看历史时，仍要符合当前阅读权限。

#### R095 为什么学校 标题等信息也要做权限过滤

这些信息帮助模型和用户区分资料适用范围，但“某个受限项目的文档存在”本身也可能是敏感信息。所以不能只过滤正文，却把全部库名和组织发给模型。

当前通过应用代码统一限制可见资料，没有启用数据库自动按用户过滤行的 RLS 功能，因此每条读取路径都必须遵守同样规则。

#### R096 忠实于资料和正确回答问题有什么不同

忠实于资料，是说回答内容能从给定资料找到支持；正确回答，还要求资料适用于用户、关键步骤完整，而且确实解决了问题。

例如，引用另一所学校的说明并准确复述，可能忠实于那份资料，却没有答对当前用户的问题。Ragas 的忠实度分数因此不能代替答案正确率。

#### R097 资料说法不一致时 系统怎样处理

先区分是真矛盾，还是学校、年份、方案或前置条件不同。条件不明确且会改变答案时追问；确实冲突又无法判断哪条适用时，应说明资料不足或请用户确认。

当前新增四道相关测试主要检验条件辨析，并非四组经确认的真实矛盾资料，所以不能据此宣称已经充分验证冲突知识处理。

### 流协议与安全实现细节

#### R104 页面如何区分进度 正文 引用和结束

服务端用不同事件名发送不同内容：status 是处理进度，evidence 是证据及判断，answer_delta 是新增文字，citations 是来源，done 是正常终态，error 是故障；拒答或澄清会通过 refusal 传文字。

每条事件还带请求编号、消息编号和递增序号。序号便于标识本次流内顺序，但没有对应的持久事件日志，因此不能用它断线后接着重放。

#### R107 前端为什么要处理半包和中文解码

网络一次读到的数据，不一定刚好是一条事件，甚至可能只有一个中文字节序列的一部分。直接逐块解析，可能出现乱码或 JSON 不完整。

当前先用流式 TextDecoder 解码，再把文字放进缓冲区，等读到事件之间的空行才解析。它服务于项目约定的协议，不代表已经覆盖 SSE 标准所有字段和边界情况。

#### R108 为什么后端已经逐步输出 页面却可能一直等待

中间代理可能先积累一批响应，再一次转发，用户看到的就不是逐步生成。项目在 Nginx 关闭响应缓冲，并发送相关响应头，Go 每次写出后及时 Flush。

前端也要正确更新页面状态。因此 Python 开始产生第一段文字，与用户实际看见第一段文字之间，还有网络、代理和渲染时间。

#### R110 慢客户端会不会影响权限撤销

为了避免撤权与输出交错，发送一段文字时会短暂持有权限读锁；撤权要拿写锁。若客户端很慢，写出和刷新迟迟不结束，这把锁就可能被占得更久。

当前有写超时作为边界，但尚未做压力验证。优化时要控制写入期限，又不能简单取消保护，让撤权后仍有旧权限数据被放行。

#### R112 Go 实现还应准备哪些工程追问

要能解释数据库连接池为什么最多十个、查询结束为什么及时关游标、用户取消怎样传到上游，以及为什么断开后另用短上下文保存状态。也要说明密码用 bcrypt 验证，令牌只存哈希，SQL 使用参数绑定。

当前没有完整的优雅退出、分布式调用追踪或生产限流。可以讨论改进，但不能把常见后端方案自动说成项目已经实现。

#### R114 为什么没有使用 JWT

当前用数据库令牌，撤销登录或禁用用户时比较直接；代价是每次请求要查数据库。JWT 可以减少部分查询，但如果要求权限立即生效，仍需要版本校验、黑名单等额外设计。

所以不能简单说 JWT 一定更安全、更适合。本项目实际用的是随机令牌，应围绕当前撤销需求解释选择。

#### R116 为什么升级前的资料和新文档默认权限不同

旧系统的资料原本供演示用户阅读，升级时直接全部收紧会改变已有使用方式；因此做了一次明确迁移，保留这些旧资料的全员阅读权。新资料则采用保守默认，避免刚上传就意外公开。

数据库记录这次迁移和审计，不能每次启动又把所有新文档改成全员可读。

#### R118 复用搜索索引时 如何避免不同用户看到同一套受限资料

为提高速度，系统会暂存已建立的关键词索引。但缓存不能只按知识库名称区分，因为同一库里，甲能看的文档可能比乙多。

当前缓存标识包含可见版本集合和权限变更编号，不同权限范围不会直接共用索引。最多保存八项，按加入先后淘汰，命中不会刷新位置，所以不是严格的 LRU 最近最少使用策略。

#### R123 历史权限检查只看最终引用的文档吗

当前更保守：新消息会记录请求范围内当时可见的文档集合，而不只记录最终引用。因此，即使某份文档没有出现在最后的引用里，失去它的阅读权也可能让整条历史回答隐藏。

好处是减少遗漏依赖的风险，代价是可能过度隐藏。以后若缩小依赖集合，需要同时考虑模型输入、范围理解和历史承接，不能简单只看答案里几个引用。

#### R124 旧回答没有记录依赖文档 怎么处理

系统尝试从保存的知识版本清单和处理记录中恢复来源，再检查用户现在的权限。如果无法恢复可靠来源，就隐藏回答，而不是默认允许阅读。

这是安全优先的兼容策略，可能让部分旧历史不可见；需要说明这种代价，而不能只说升级完全不影响使用。

#### R126 原文件下载如何防止绕过权限

下载入口先根据版本找到所属文档，再检查当前用户能否阅读，不能把文件目录直接暴露成静态下载地址。响应以附件方式返回，并设置不要猜测内容类型的响应头。

不存在和无权访问尽量使用一致提示，减少别人枚举资料的机会。不过具体接口并非都返回同一状态码：文件为 404，会话创建非法范围为 400。

#### R127 登录令牌存在浏览器里 有什么风险

当前令牌放在 sessionStorage，通常只在当前标签页会话使用；但如果同源页面出现 XSS，恶意脚本仍可能读取它。用模板按文本展示回答有帮助，但不构成完整 XSS 防护。

改用脚本不可读的 HttpOnly Cookie 是一种选择，同时也要处理 CSRF、SameSite 和跨域问题，不能只换存储位置就说所有登录风险都解决了。

#### R129 日志和审计分别记录什么 如何避免泄漏

审计记录谁修改了哪个权限；处理追踪则用于查看搜索候选、模型阶段和错误。对外模型错误只保留分类和状态码，避免原始异常带出凭据或正文。

详细原文、答案和评测文件不进入 Git。当前消息追踪仍可能包含用户当时可见的候选内容，生产化时还要限制谁能看、保留多久，以及哪些内容根本不应返回页面。

### 指标 实验与预算细节

#### R132 D 相对 A 提升了多少 怎么表述才准确

必要依据平均 Recall@5 从 78.65% 到 94.48%，增加 15.83 个百分点；辅助答案正确率从 66.25% 到 90%，增加 23.75 个百分点。

“百分点”是两个百分数直接相减，不等于相对提高了相同百分比。后一个对比的两组也并非都经过人工裁决，因此应保留“辅助评分”的限定。

#### R134 完整覆盖和 MRR 分别反映什么

完整覆盖要求一道题需要的全部依据都进入前五段，适合看组合问题有没有缺一半。MRR 则关心首次找到完整一处指定依据时，要看排名前几段，再取该位置的倒数。

项目这个 MRR 不要求全部依据首次同时齐全。拒答和澄清题不适用这些搜索指标，记为空值，不能补成零再混算。

#### R138 新增 40 道跨库题包含哪些场景

它们分成 10 道开发题和 30 道测试题，预期行为为 27 回答、8 澄清、5 拒答；场景包括比较、歧义、多轮、条件辨析、无答案和正常对照。

其中 25 题与旧题共享来源段落，四道条件辨析也不是真实矛盾材料；多轮主要直接提供固定历史。所以它是新的跨库评测流程，不代表所有事实都未被接触，也不代表真实完整会话测试。

#### R139 六项权限测试为什么不算进答案正确率

这些测试检查的是：用户无权看的正文或元数据，会不会进入模型或返回给用户。覆盖跨库、同库不同文档、默认范围、非法指定范围、历史撤权和在途撤权。

通过权限检查，说明访问控制符合测试约束，不代表知识回答正确。因此要单独报告工程测试通过数，不能往 40 道知识题分母中再加六道来算高分。

#### R144 引用合法率 100% 为什么不等于所有回答都有正确引用

引用合法率只看实际出现的来源编号里，有多少真的指向本次资料；一个答案完全没引用，也不会进入这个编号分母。

因此还要看“可回答题中，有多少完整结束并带了合法引用”。旧 D 报告两项分别是 100% 和 96.875%。两者都不能单独证明引用原文确实支持每句话，那还涉及语义判断。

#### R148 小样本高分 如何解释可信度

先给分子分母和场景，不只给百分比。题目来自同一事实或会话时，它们并非完全独立；同题比较还要看哪些改善、哪些退步，而不是只看两个平均数。

进一步可按事实主题或会话计算置信区间，或做配对统计检验，但当前工具完成不代表已经做过显著性分析。多造几种问法，也不能当作获得了同样多的新独立事实。

#### R149 什么变化需要重新发布测试集

原文、必要事实、引用位置或开发测试划分改变，都可能改变评分标准，需要重新审核并发布新版本。旧题、答案和人工裁决应保留，不能覆盖后仍声称是原实验。

不同环境重新导入文档会产生新 ID，也需要核对映射关系。不能把原生环境的固定清单直接拿到 Docker 数据库里使用。

#### R152 为了排查错误 需要保存哪些处理记录

记录每路找到了哪些段落、融合和重排后的顺序、哪些被淘汰、最终五段用了多少字符，以及模型各阶段耗时。这份记录叫 trace，用来还原一次请求经过了什么。

还会保存重复正文、最终输入的校验指纹等。旧单库只拿到重排前五项，不能在报告里假装知道其余候选排第几；记录是否完整也要标明。

#### R153 有处理记录 就能证明换方案一定更好吗

不能。记录可以证明“这条依据在重排后消失”，但不能直接证明换排序算法后，所有答案就会变好；新方案也可能引入别的错误。

要固定其他条件，针对同一批题比较新旧方案，并保留改善和退步。没有命中指定原句，也不一定完全没有语义等价的依据，这需要结合实际内容判断。

#### R156 为什么只允许从原问题摘取子任务

如果让模型自由改写，它可能添加用户没说的学校、年份或操作条件。限定为原文连续片段后，程序可以直接检查输出是否确实来自用户问题，降低问题被改成另一件事的风险。

代价是有些表达必须重新组织语言才好拆，这套方案就做不到；前置关键词判断也可能漏掉复合问题。因此它是受控实验，不是通用自主规划器。

#### R158 查询拆解会增加多少调用

一道触发拆解的题，最多增加一次拆解模型请求和两次子查询向量请求，即不算重试新增最多三次模型 HTTP 调用。后台还要对各库多执行相应搜索，数据库工作量也会增加。

它不是让模型多写两份答案。当前尚无真实拆解效果和费用结果，不能把理论调用数当作实测节省或收益。

#### R159 为什么同一道题的新旧方案要交错运行

如果先跑完全部旧方案，再隔一段时间跑新方案，网络和模型服务负载变化可能被误算成方案差异。逐题交错，让同一题的两个结果尽量在接近时段生成。

固定 seed 让本地题序和先后顺序可重现，但不能冻结提供商内部模型。实际路由、配置和故障仍然需要记录。

#### R161 如何避免实验中断后把调用预算重新算零

每次发模型请求之前，先把“将发出一次请求”写入本地日志，记录属于哪题、问答还是评分，以及第几次尝试。续跑时读历史日志，从共享上限扣除已发请求。

所以重启不能简单再领一份新预算，重试也要计数。当前会刷新日志缓冲，但没有证明突然掉电时也达到磁盘级绝不丢记录的保证。

#### R162 限制 150 次调用 为什么不等于限制金额

每次请求文字多少、输出长短、是否命中缓存和模型单价都不同。次数上限可以限制请求规模，却不能精确封顶账单。

当前开发实验提案是共享 150 次 HTTP，费用约 1–3 元只是估算，仍待预算确认。请求已发却没收到用量时，费用应记未知；不能把“没记录到”当作免费。

#### R163 为什么不能不断重跑直到答案通过

模型可能有波动，只保留最好的一次会隐藏系统真实失败率，也少算重试费用。新跨库入口因此保留已保存的终态；尚未执行的题仍单列，不能自动变成成功。

如果修复代码后重跑，应开新的运行版本，并保留旧失败结果。实验也允许无改善或退步，不能为了得到好看的简历数字强行发布。

#### R164 新的跨库优化目前完成到哪里

已完成实验工具、问题与原文审核、40 题固定发布，以及六项权限测试；最新记录包含 82 项 Python 测试和独立 Go/Python/SQL 联测通过，这些主要证明控制逻辑可以运行。

真实模型开发实验还没开始。后续需要先跑开发题、决定是否保留拆解，再跑正式题并人工裁决，才能填写跨库成绩或效果提升。

### 模型协议 运维与现场练习

#### R166 直接调用厂商和通过模型网关 有什么协议差别

厂商原生接口可能把参数放在 input、parameters 等嵌套字段里；网关则统一为 input、dimensions，或 query、documents、top_n 等字段，返回的序号名称也可能不同。

适配层要显式转换，不能只改地址。网关里的 chat、embedding、rerank 是能力路由名称，不能替代背后实际模型版本的记录。

#### R168 通过私有证书和隧道连接模型网关 为什么仍要验证 TLS

隧道可能改变实际连接到的机器地址，但不应改变“服务器应该是谁”。当前允许连接到宿主机隧道，同时保留逻辑域名作为 Host 和 TLS 校验身份，并加载指定的可信 CA 证书。

网关要求 HTTPS 和 /v1 路径，拒绝在地址里夹凭据、查询参数等，并关闭自动跳转及环境代理继承。这里没有通过关闭证书验证来解决连接问题。

#### R177 为什么出处和处理记录使用 JSONB

页码、章节、引用和搜索诊断的字段比较灵活，用 PostgreSQL 的 JSONB 可以把这类结构化内容一起保存，方便追溯当时情况。

代价是字段约束较弱、复杂查询不如关系表直接，也容易让聊天记录变得很大。稳定关系如用户组仍单独建表；资料量增加后，可把详细诊断移到分级归档存储。

#### R181 健康检查通过 能证明应用可用到什么程度

Go 和 Python 主要检查数据库能否连接，Web 检查页面入口能否访问；服务依赖配置控制启动顺序，重启策略处理进程退出。

它们不能证明模型有额度、资料能正确搜索、流式答案完整或回答正确。健康检查适合发现基础故障，不能替代从登录到问答的业务验证。

#### R186 Windows 开发有哪些值得讲的真实问题

项目曾因环境文件加载路径问题没有读到根目录配置，后续补了回归测试；Python 数据库异步连接还需要兼容的 Windows 事件循环，由启动入口统一处理。

另外，原生环境和 Docker 的端口、数据卷和文档 ID 不同，测试时不能混用。可用这些案例说明配置和环境隔离能力，但它们不是模型效果优化。

#### R187 为什么 CI 测试结束后 仍可能卡在清理阶段

后台常驻的 uv run 可能继续持有缓存锁，即使测试已结束，后续缓存清理仍会等待。当前做法是直接用已建虚拟环境的解释器启动服务，并记录进程 ID。

退出时先终止再等待后台进程结束，避免锁还没释放就进入下一步。还要保留原测试失败的退出码；这是进程生命周期问题，不能算作 RAG 正确率提升。

#### R198 面试现场最值得练哪些代码

优先练两路排名合并、字符区间覆盖判断、数据库领取任务和发布前校验、同会话生成互斥、网络半包解析，以及请求取消后保存终态。这些都直接对应项目难点。

写完再构造重复请求、两个执行者竞争、无权限、输出截断和空输入等反例，说明代码在失败时如何表现，而不只演示正常输入。

#### R199 面试官说只是接了几个 API 应如何回应

可以承认项目没有训练模型，再用一个实际问题说明工程工作：新文档处理失败不能破坏旧版，撤权要协调后续输出，或从八道失败里发现五道主要缺在初次搜索，进而设计受控实验。

重点是解释选择、代码机制和验证证据，也说明剩余漏洞。比起堆组件名，这更能展示把不确定的模型能力做成可维护应用的能力。

### 十条容易失分的表述

1. 把“旧单库 144/160”说成全部问题或跨库 90%。
2. 把 Recall@5、完整证据覆盖、忠实度、引用合法率和答案正确率混为一谈。
3. 说用了 HNSW、Redis、Kafka、语义切片、父子块或文本去重，而当前代码没有。
4. 把 8000 字符说成 8000 token 或总 Prompt 上限。
5. 说幂等会自动重放旧回答，或者 seq 意味着支持断线续传。
6. 说撤权可以收回已传给用户或模型的内容，或者本地锁天然支持多实例。
7. 说模型别名未变就能保证实际权重和向量空间不变。
8. 把 82 项替身单测、六项权限协议或来源审核当成真实模型正确率。
9. 把云端准备、Compose 文件或健康检查说成生产部署及 SLA 已通过。
10. 把诊断发现或实验工具完成说成拆解已提升效果。

### 演示与复习顺序

先展示有出处的单库问答，再展示 VPN 学校澄清与双方来源比较；随后打开一个文档的版本、切片和授权；用历史记录解释更新与撤权的差别。最后展示旧冻结报告、八题失败归因以及新跨库冻结与盲审工具，清楚指出新真实实验尚未执行。演示不需要临场运行付费全量评测。

闭卷应能画出上传发布、在线问答、权限撤销和离线实验四条链，并标注每个数据库事务、外部调用、幂等键、版本身份和无法原子保证的窗口。每个“以后可改”都要能说明触发条件、验证方式与代价，不把路线图当作已交付功能。

外部原理参考仅用于解释组件：pgvector 官方 README、PostgreSQL SELECT 文档、rank_bm25 项目说明及 MDN SSE 文档。项目实现和历史成绩以本章标注的代码与冻结报告为依据；供应商实时价格、云端运行状态及远端 PR 状态不由历史记录推断。
