## 1. 已确认的需求

- 项目用于求职展示，展示可运行、可评测的 RAG 系统及 Go 后端工程能力。
- 首期包含 Web 问答、知识管理和离线评测。
- 知识来自原 PRD 附带的文档，用户导出文件后上传，不直接读取飞书链接。
- 大模型使用 DeepSeek 的 deepseek-v4-pro；Embedding 使用阿里百炼的 qwen3.7-text-embedding；重排序使用阿里百炼的 qwen3.7-text-rerank。模型名称由用户确认。
- 阿里百炼北京业务空间 API Host 已确认，实际地址仅保存在本地配置。Embedding 建议显式使用 1024 维。
- 飞书机器人后续迭代；人工工单、部门权限和业务效果看板不属于首期。
- 开发采用 spec 驱动；技术方案需人工确认后才进入应用代码编写，交付前验证并提交 commit。

## 2. 首期细化方案

### 2.1 知识管理

- 建议先支持文本型 PDF、DOCX、Markdown 和 TXT。PPTX、表格、网页抓取、OCR 留到扩展阶段，此项为待确认的格式收敛。
- 单文件默认不超过 20 MiB；超限、不支持或无可提取文本时给出明确错误，不能把空解析标为成功。
- 文档需有标题、知识库/适用组织、来源说明；不同学校和制度来源分库管理。
- 列表展示文档、版本、处理状态、启用状态、失败原因；支持上传、重试、切片预览、启停和上传新版本。
- 解析、切片、向量化异步执行；处理状态与启用状态分别记录。
- 同一文档新版本处理成功后原子切换，旧版退出新请求的检索范围；处理失败时旧版继续可用。
- 同一知识库内重复上传相同内容提示已存在；不同知识库可导入相同素材。
- 文档停用后，后续新请求的检索、上下文和推荐结果均不得包含该文档；在途请求绑定其开始时的知识快照。
- 历史回答保存引用快照，包括版本、原文节选、页码或章节。旧版文件保留以供历史引用查看。
- 首期采用停用而非永久删除，保留可复现的评测及历史引用。

### 2.2 Web 问答

- 用户选择一个知识库后提问；一次会话绑定该库，防止适用组织混用。
- 支持新建会话、历史会话、多轮知识追问；不执行权限申请、安装软件等操作。
- 使用有界历史上下文改写追问；改写不得把旧答案直接作为新事实证据。
- 检索链路包括向量检索、BM25、融合和重排序；各阶段可独立评测。
- 证据不足返回拒答提示；冲突证据无法确定有效来源时说明冲突，不输出确定结论。
- 回答流式展示，事实性内容使用引用标识；用户可查看来源版本、页码/章节、节选与原文件。
- 超时、模型故障、检索为空、流式中断分别显示可理解的状态；中断回答不能计为完整成功。
- 同一会话同一时刻只允许一个生成任务；重试关联原请求，避免重复写入用户消息。
- 保存重写问题、候选来源、最终引用、模型/策略版本、耗时和可获得的 Token 用量。

### 2.3 基础访问控制

- 首期提供普通用户和管理员；知识管理接口仅管理员可用，用户只能访问自己的会话。
- 暂不做部门级文档权限或企业 SSO；知识库选择是适用范围过滤，不代表部门权限隔离。
- 模型凭据仅在服务端配置；原文件通过受控下载接口读取，不暴露存储目录。
- 原始文档、对话、评测输出和 API Key 不进入 Git。外部模型调用仅使用用户配置的服务。

## 3. 评测与验收

### 3.1 数据集

- 用实际导出文档构造 200 条有来源依据的黄金样本，不用生成的虚构制度代替实际素材。
- 另设开发/校准样本，不用冻结的最终测试集调阈值或 Prompt。
- 最终测试集建议包括：单文档问题 100 条、多轮问题 30 条、同一适用范围内多文档问题 30 条、无答案问题 25 条、来源冲突/适用范围问题 15 条。
- 样本保存问题、历史上下文、知识库、文档版本、证据定位、期望行为、必要事实和场景标签。
- 人工确认参考答案和关键事实后冻结数据集；数据集变更单独版本化。
- 支持在草稿中新增、修改、停用样本并发布新版本；已发布版本和历史报告不可覆盖。样本保留稳定 ID、修订号、变更原因与审核记录。
- 文档变更后按来源依赖及问题相关性生成受影响清单，AI 可提出证据重定位、答案修订和新题草稿；人工审核后发布与新语料匹配的评测版本。
- 无答案、跨文档和冲突样本也需检查，不能只更新直接引用变更文档的题目。维护流程详见技术方案第 8.7 节。
- API Key、服务地址和实际私有素材不提交；Git 保存格式定义、评测脚本与匿名化报告模板。

### 3.2 指标口径

| 指标 | 定义 | 首期目标 |
| --- | --- | --- |
| Recall@5 | 可回答样本中，最终 Top-5 覆盖的必要证据组数 / 必要证据组总数，再按样本平均；同组等价来源只计一次 | ≥82%，待实测 |
| 答案正确率 | 可回答样本满足必要事实且无矛盾、无错误适用组织的比例；拒答不算答对 | ≥85%，待实测 |
| 正确拒答率 | 无答案/无法消解冲突样本中正确拒答或说明冲突的比例 | 单独报告并人工评审 |
| 引用有效率 | 引用标识能解析到本次授权证据和保存版本的比例 | 100% |
| 引用支持率 | 被引用的事实性陈述确实受原文支持的比例 | 单独报告并人工抽检 |
| TTFT | 用户发送到首个答案内容片段渲染；加载提示不计首字 | 报告 P50/P95，P95 <2 秒为优化目标 |
| 完整回答耗时 | 用户发送到回答、引用与终态渲染结束 | 报告 P50/P95，P95 <5 秒为优化目标 |

- 忠实度可用模型评分辅助分析，不等同于答案正确率；固定评测模型、评分提示和数据版本，并人工抽检。
- 黄金证据标到原文版本与段落，不直接依赖 chunk_id；切片策略变化后重新映射，无法映射的样本须修复后再比较。
- 自动评分、人工修订与抽样复核结果分别保存；评分失败不得默认为正确，也不能无记录地移出分母。
- 比较 BM25、纯向量、混合检索、混合检索加重排；相同知识快照与评测集下记录结果。
- 每次报告记录语料规模、切片数量、API 模型、向量维度、回答长度、并发、运行环境和策略版本。
- 质量评测真实调用 API；普通自动化测试使用接口替身验证失败、中断和版本一致性，不把替身结果计为模型效果。
- 未进行真实评测前，不能声称达到正确率或延迟目标。100 QPS、99.9% 可用性及人工咨询下降不属于首期验收。

执行流程、实现模块和回归方法详见 [技术方案第 8 章](technical-plan-v1.md#8-验证与交付)。

### 3.3 交付证据

- Windows 原生开发说明及 Docker Compose 启动配置；支持 Linux 云服务器单机部署，数据库和上传文件持久化，模型与运行配置由环境注入，公网经 HTTPS 入口访问。
- 完整的上传、解析、问答、引用、停用、版本替换、失败重试演示。
- 200 条冻结评测样本及可复现脚本；私有数据本地保管，通过清单和内容校验值记录版本。
- 基线对比报告、失败样本分析、参数与 Prompt 版本记录。
- 每批实现有对应 commit，应用代码交付前通过相应验证并由用户确认。

## 4. 首期里程碑

1. 方案确认与基础接入：服务骨架、数据模型、身份和模型适配器。
2. 知识管理闭环：文件处理、版本发布、切片、检索和启停。
3. 问答闭环：多轮改写、重排、拒答、流式输出、引用及历史。
4. 评测与展示：真实素材、黄金集、消融实验、验证报告及演示文档。

不将原 PRD 的六周计划视为已承诺工期；先确认模型接口和素材条件，再估算。
