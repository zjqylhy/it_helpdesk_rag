# 第二阶段技术方案

日期：2026-10-10

状态：2026-10-10 用户已确认。对应 [第二阶段需求规格](spec-v2.md)，各批实际完成及验收状态见 verification.md，不代表所有能力已经实现。

2026-10-12 用户确认优先实施效果评测；本文旧 20/60 题安排及 A→B→C→D 顺序以 [效果深度技术方案](technical-plan-effect-depth.md) 当前批次为准，其余工程与业务范围保留。

## 1. 保持现有架构并增量迁移

- Go 负责账号/授权、问答入口、反馈复核、指标业务口径及生成准入；Python 负责已授权语料的检索、模型调用、导入和评测；Vue 增加权限配置、反馈与管理员看板。
- PostgreSQL 保存业务记录和授权关系；保留 pgvector、进程内 BM25 及单实例 Compose。暂不引入 Kubernetes、独立搜索集群或对象存储。
- 数据库新增有版本号的迁移记录，迁移幂等；在独立副本验证旧数据升级和回滚操作。含不可逆数据变化时先备份再恢复，不使用粗暴 DROP 回滚。
- 不重算现有 Embedding；发布快照仍不可变，权限作为独立、实时的访问条件。qa-v2 原始离线报告/清单格式保持兼容。

## 2. 授权数据与一致性

### 2.1 拟新增字段与表

| 数据 | 用途 |
| --- | --- |
| users.disabled、usage_kind | 停用账号；标记真实参与者、演示或测试来源 |
| user_groups、user_group_members | 组及成员关系，唯一成员约束 |
| documents.visibility、document_group_grants | all_users / groups；空组仅管理员可读 |
| authorization_state.revision | 授权变更单调版本，参与请求校验及缓存隔离 |
| audit_events | 管理操作、权限与成员变更，不保存密码或原文件正文 |
| messages.provenance、usage_kind、strategy_version | 回答依赖、不可变运行来源及策略归属 |

采用一个权限版本记录作为单实例初版的一致性边界，组/成员/可见性修改与版本递增同一事务完成。全局版本可能导致无关生成也中止，优先保证安全，后续再优化为按主体版本。

### 2.2 问答全链路

1. Go 校验账号、会话归属、请求范围及当前可见文档；拒绝未授权指定库，默认范围取当前可见业务库。
2. 通过内部认证携带服务端确定的主体和权限版本到 Python；客户端不得传可信用户组或可读文档清单。
3. Python 从数据库重新计算文档授权集合，在导出原文、向量检索和 BM25 建索引前与快照版本集合求交；模型组织选择列表同样只来自授权元数据。
4. BM25 缓存键包含有效文档版本集合校验值及权限版本；不以只有 snapshot_id 的缓存共享受限语料。
5. Go 在输出与持久化时检查引用/来源依赖及授权版本；所有引用必须可追溯到文档。记录生成 consulted 文档/元数据依赖以覆盖无引用的澄清、拒答和失败。
6. 权限变更与流输出采用单 Go 实例的统一同步边界；撤销操作阻止新流片段、取消在途生成、提交授权变化后再确认。用户自停用/管理员停用同样处理。
7. 权限变更导致生成中止时保留内部审计，但用户读取接口遮蔽不再可读的内容。不对流式生成自动重试。

权限检查包括各 API 的文档、版本和知识库 ID 关系，防止拿授权 document_id 拼接其他文档 version_id。内部 RAG 不发布宿主端口，仍校验内部令牌及服务端主体。

### 2.3 历史与账号

- 历史获取逐消息检查依赖，受限答案整体遮蔽，不仅删掉引用。trace、快照成员、知识库名称等按同一原则清理；历史补充不能把隐藏答案加入改写上下文。
- 老消息无完整 provenance 时保守采用保存快照的全部依赖；无法验证依赖则遮蔽，不能默认放行。用户自写问题可保留，自动摘要/组织信息不能绕过权限。
- 反馈处理涉及已撤权原答案时，普通用户接口也执行遮蔽；管理员只通过受审计的反馈复核入口查看被主动提交的材料。
- 账号停用使现存 Token 失效；现有环境账号继续作为引导账号，新用户从管理员页面创建。密码继续 bcrypt、保持既有长度限制。
- 旧文档迁移明确 all_users，新文档默认 groups 空集合；上传新版本继承当前 document ACL。
- 负例用隔离数据库及模型替身，并断言发往模型的正文与组织候选不包含受限内容。模拟并发撤销与 SSE 发送，不仅断言 HTTP 状态。

## 3. 反馈和问题处理

### 3.1 数据与接口

- answer_feedback：message_id 唯一的当前反馈、提交者、质量判断、解决状态、原因、修订号及时间；所有者校验、终态校验、幂等提交和并发更新冲突控制。
- feedback_events：每次提交、修改、撤回的追加事件；复核结论绑定明确 feedback revision，修改后的反馈显示待重审，不静默继承旧裁决。
- feedback_reviews：正确/错误/无法判定、审核者、原因；用户反馈与管理员判断互不覆盖。
- quality_issues、issue_feedback_links、issue_events：问题归因、重复反馈聚合、处理状态、负责人、修订关联、回归证据和重开记录。
- 回归验证不只填写“已修复”，需关联知识版本或策略 commit 以及可核对的回归记录。外部模型判分辅助人工结论。
- 拟增加 `/messages/:id/feedback`、管理员 `/feedback` 与复核入口、`/quality-issues` 及 `/dashboard/business`；权限管理使用独立管理员路由。实现时给出接口规格和错误码。

### 3.2 指标聚合

- 业务聚合从 PostgreSQL 中终态消息、当前反馈、有效复核和唯一问题状态计算；不把 Prometheus Counter 作为可修改反馈的真值。
- 回答指标按消息创建时间和查询截止时的当前状态；修复率按问题创建时间、截止时状态及其确认错误属性。界面显示时区、数据更新时间及该口径，允许审计历史事件重建。
- 用户解决状态与质量判断独立。对 clarify 强制 resolution=not_applicable；质量误报也可反馈，但不进入解决率。
- 反馈撤回不删除事件、不计当前有效反馈；一个 message 多次修改不增加分母。无法判定不计复核错误率分母，单独显示数量。
- 已复核错误且关联 issue 的反馈改动不自动抹掉已确认问题，管理员重审并记录是否撤销原结论。
- 数据来源创建时从服务端账号和可信评测/压力运行确定，写入 message；旧数据回填 demo，不能凭普通请求 JSON 伪装成真实使用或回写历史来源。
- 自测记录与真实记录分区筛选，默认 real_usage，零数据为空态。跨库按唯一回答汇总；按知识库细分须说明同一回答可关联多个库，不能相加作为总量。
- 已保存普通用户对话不因看板而公开；首版聚合及问题列表仅管理员可见。原有 200 题成绩独立于业务反馈看板。

## 4. 工程观测与保护

- 每个请求生成 trace_id，通过 Go → Python → 模型调用关联。结构化日志记录阶段、状态、耗时、故障类别，私有正文仍留受控数据库。
- 增加 Go/Python 的 Prometheus 指标和可选观测 Compose 配置，用于请求数、错误数、耗时直方图、在途、等待及导入任务；采集端点内部受控，Web 不转发。
- 指标标签仅用有限集合的路由模板、阶段、模型和状态；用户 ID、message_id、问题正文、任意 URL 不作标签。请求标识用于日志关联。
- 提供管理员工程概览及本地告警规则验证，覆盖持续错误、生成等待/超时、导入失败与服务不可用；本轮不配置向外发送邮件或飞书通知。
- 首版建议可配置默认：单用户最多 1 个在途问答，全局最多 3 个执行、6 个等待，等待上限 10 秒、完整请求上限 120 秒。登录按来源地址限流，问答按身份限流；仅信任显式配置的反向代理。
- 过载使用 429/503 与安全重试提示，拒绝的请求不算完成回答；模型执行、等待和数据库记录分别观测。取消需传递到 Python 和外部流读取并释放执行名额。
- 每日问答/模型调用配额在数据库按统计日期原子预留；模型重试也占配额。没有发出模型请求的预留可释放，已发出但取消或用量未知仍保守计一次；停用、重启不能清零当日配额。
- 熔断按模型依赖维护，连续故障达到可配置阈值后短时拒绝并半开探测；不将鉴权/参数错误当作可重试临时故障。保留既有重试预算，重试计入用量。
- 暂不引入备用模型：固定真实模型便于评测归因，故障明确返回未完成，不用替身或无证据答案冒充降级成功。
- 每批评测/真实压测显式限制模型 HTTP 请求次数（包含重试）。先用开发样本记录调用和 Token 分布，再提供整批预算；预算耗尽停止并保存未完成状态。未知用量不记为零，金额估算需记录价格日期，与账单区分。

监控设计参考 [Prometheus instrumentation](https://prometheus.io/docs/practices/instrumentation/) 关于请求、错误、延迟及标签基数的建议。

## 5. 跨库评测扩展

- 现有 runner 直接调用单库 `Pipeline.events`，不能原样当作联合问答评测。新增明确的 scope 模式，进入与 Web 共用的授权后跨库流水线，旧模式继续复现旧报告。
- 扩展样本保存 scope_mode、kb_ids、成员快照、期望组织/文档、测试主体/组夹具、history、expected_behavior 与必要证据组；保存有效授权清单校验值。
- 问答模式同时测试 Web 的会话历史承接；固定历史单步重放与真实多轮会话分开标注。未授权来源不能因离线 admin 默认权限意外加入上下文。
- 原始语料来源与权限安全夹具分开，题目按事实主题隔离；新 schema 版本不得改变旧 JSONL 的序列化校验值。
- 一次检索命中两个比较对象不等于回答正确；检查各对象必要事实、组织归属和引用语义支持。按证据组区分“任一等价来源”与“必须组合来源”。
- 保留逐阶段候选及排名，失败报告支持按场景/主因/组织筛选，提供问题、实际回答、标准、证据和人工裁决入口。
- 正式冻结前人工审核候选；正式运行前根据实测提供调用预算，首轮完整 60 答案人工裁决。辅助评分不替代正式裁决。
- 小样本开发通过后只承诺执行正式评测和披露结果，不承诺某个真实模型一定达到目标。若正式失败需修订，使用开发集改进，保留原运行及新版本清单。

评测设计参考 [微软 RAG 设计与评测指南](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/rag/rag-solution-design-and-evaluation-guide) 关于代表性样本及分阶段评估的建议。

## 6. 验证和交付顺序

| 批次 | 交付 | 主要证据与人工节点 |
| --- | --- | --- |
| A | 用户、组、文档授权，历史/SSE 保护 | 旧数据升级、端到端安全负例、并发撤销、页面人工验收 |
| B | 反馈、复核、修复与看板 | 重复/修改/撤回、零分母、复核过期、唯一问题统计、来源隔离、人工业务闭环验收 |
| C | 观测、准入、故障和部署准备 | 无付费替身压测、有限真实调用、恢复演练、报告与监控证据 |
| D | 跨库评测工具、候选和报告 | 开发/正式主题隔离、人工题目审核、预算清单、全量答案裁决与失败分析 |

- 每批完成适当 Go/Python/前端检查及跨服务联测，验证后 commit，再更新实际验证记录。文档中的计划不混入“已实现”。
- 本地压测使用独立项目、端口、数据库和测试账号；不将测试反馈混入真实数据，不停止其他项目，不删除当前命名卷。
- 完整备份恢复使用独立空目标实例，核对全部文件及版本，验证权限、反馈、历史和一次问答；标注恢复耗时与演练条件。
- 云端仍单机部署，补充实际资源所需步骤；版本发布记录应用代码与迁移版本，回滚先确认 schema 兼容性和备份，不承诺任意旧镜像可直接读新 schema。
- 最终交付披露质量成绩、性能边界、真实反馈样本数以及待云资源项；没有真实用户时只验收采集/统计能力，不填写虚构业务收益。

## 7. 本次需要确认的具体方案

1. 原 200 题保留，新增 20 开发题和 60 正式跨库题；候选和实际答案各有一次人工审核。
2. 旧文档显式全员可读、新文档默认仅管理员；指定组授权为 OR，撤销后遮蔽旧答案并中止在途输出。
3. 反馈来源严格区分；无真实参与者时默认真实指标为空。首版仅管理员看板，不接入工单系统。
4. 按 A → B → C → D 实施；本轮无真实云部署和企业 SSO，完成本地证据及可部署方案。
