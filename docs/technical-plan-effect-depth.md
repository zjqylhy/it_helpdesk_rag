## 1. 现状及兼容边界

- `evaluation/runner.py` 使用旧单库 `Pipeline.events`、单库 Case 和 export_snapshot；尚无正式 scope 评测入口。多库真实功能已存在，但不等于评测入口已适配。
- `AuthorizedStore` 在语料/向量检索前过滤授权版本。新增评测复用这条边界，不能用 admin 默认主体绕过权限。
- `scope_snapshot` 读取当前成员；冻结重放需显式绑定成员快照及授权集合，不能在旧发布目录下悄悄使用最新成员。
- 旧 `qa-v2` 发布集、JSONL 序列化及 A/B/C/D 入口保持可复现；新 scope 入口只比较当前 D 与实验策略，不命名为原 A/B/C 消融。

## 2. 阶段观测及归因工具

扩展私有 trace 保存 BM25/向量候选、融合序列、完整重排索引与分数、选择前后 ID、预算占用、淘汰原因和最终上下文哈希。记录路由请求/实际范围及必要比较对象；只保存已授权内容。正文、答案和详细候选不进入公开日志或仓库。

淘汰原因分别为融合上限、Top-K、重复证据、预算不足、权限和路由排除，不以统一“召回失败”覆盖。阶段独立耗时，服务端首字与完整回答计时在辅助评分之前结束。

新增离线诊断命令：读取冻结 Case/语料和运行记录，按区间覆盖重算各证据组状态，再结合事实裁决生成逐题审核页。支持多因标签和人工修正；历史缺少的重排分数/序列显示缺失，不能反推成精确数据。因果判断标为可证实、推断或待复核。

回归覆盖：候选外缺失、融合损失、重排损失、预算丢失、证据齐全但答案漏事实、等价来源、人工作用与辅助评分分离。历史 30 题重算与原 Recall@5 一致作为兼容检查，不重跑模型来替换历史答案。

## 3. 跨库数据模型、冻结及执行

独立 `ScopeCase`/schema 版本，不改变旧 Case：scope_mode、请求 kb_ids、冻结成员快照、期望路由/组织、主体夹具、history/会话链、预期行为、必要事实/证据组、主题和审核记录。证据组内允许替代、组间必须组合；可标记单个子任务预期拒答而整体允许部分回答。

发布清单绑定题目与语料哈希、成员快照、组织元数据、default_search 配置、授权文档版本集合哈希、主体组夹具及发布版本。不同环境 ID 重新映射后必须重新核对并发布；不能直接把原生冻结 ID 用于 Docker 数据。

scope runner 在隔离数据库加载冻结成员及权限夹具，通过与 Web 相同的 AuthorizedStore 和 scope 流水线执行；构造固定成员读取视图，拒绝成员/配置/授权漂移。会话链另走 Go 接口检查真实历史过滤与承接；固定历史重放和 Web 会话链分别汇总，不混算延迟或重复计题。

续跑键包含数据/语料/权限、代码 commit、模型实际路由、模型配置、提示、拆解配置、排序 seed、输出协议及价格版本。中断保留 attempts 和已发出调用；最后状态汇总不丢掉历史费用。不兼容清单拒绝续跑。

工程回归使用模型替身和独立数据库：固定成员漂移、未授权证据/组织元数据、组织切换、冲突/不足证据、真实链前轮失败、撤权历史及在途流输出。不会修改现有演示业务数据。

## 4. 第一项受控实验：复合查询拆解

选择依据：历史八题中 5 道主因是候选召回；上下文预算未耗尽。先验证拆解能否提高必要证据进入候选池的概率，证据去重/分配保留为后续独立方向。

| 固定项 | 设置 |
| --- | --- |
| B0 | 当前 `qa-v3-scope` D 流程，不拆解 |
| B1 唯一实验变量 | 路由后对复合检索问题拆成最多 2 个子查询，保留原查询并合并候选 |
| 范围与权限 | 两组使用同一冻结主体、成员、授权范围和组织约束；子查询不得扩库 |
| 模型与生成 | 相同真实模型路由、温度/采样配置、重排、充分性判定和答案提示 |
| 证据预算 | 两组均使用现有 Top-5 与 8000 正文字符；融合候选上限保持当前 scope 的 40 |

拆解使用一次结构化模型调用，最多 2 个子查询；每个子查询只增加一次 Embedding，逐授权成员 BM25/向量检索。保留原查询，按固定 RRF 与库轮转规则合并，候选总数不增加，再执行原有统一重排和对象保留逻辑。该合并是拆解的必要组成，不同时引入去重、扩大 Top-K 或改答案 Prompt。

拆解结果校验组织、约束、子查询数量和长度。格式错误回退原查询并记录失败/调用费用；问题已经需要澄清/拒答时不拆解，不绕过原路由判断。单纯单任务沿用原查询。每道复合题相对基线新增至多 3 次 HTTP 请求（拆解 1、额外 Embedding 2；不含重试），实际成本由账本统计。

先运行 10 开发题及独立权限回归，检查证据覆盖、错误拒答和实际用量。若拆解无改善或引入权限/路由退步，保留开发负结果并保持基线；不得为了完成“优化”强行发布。正式集可照常建立基线，但不以同一正式集反复筛策略。

锁定策略后，两组在同一 30 题正式集成对执行，按固定 seed 交错顺序减少时段影响，warm-up 与评分调用另记。以每题请求边界统计问答延迟，将澄清/拒答、完成、故障分层展示；失败耗时和失败率单独列出，不能只留成功快样本。40 题真实集合两策略一次重放最多 80 条答案（开发 20、正式 60），不是 80 次 HTTP 请求；真实调用预算另行实测核算。

只对实际生成的答案做人工成对裁决；随机左右顺序、隐藏策略名、提供同一标准和冻结原文。汇总净改善、错误拒答、延迟与成本及分场景变化，明确样本量和缺失值。保留所有策略输出，不重试选取更好答案；协议允许的故障恢复单独记录。

## 5. 验证与提交

实施依次为诊断/trace、scope schema/冻结/runner、审核包和权限联测、B1 开发实验、锁定后正式运行及人工汇总。Python 检查覆盖新 runner 和旧评测兼容；涉及 Go 会话接口时执行 Go test/vet 和跨服务联测；修改审核页面时执行浏览器校验。只做本次改动相关检查。

最初规格提交只含需求、技术方案和历史只读诊断：核对 30 题的指标、八题归因表、40+6 配额、相对文档链接、旧文件 SHA256 和 git diff。后续代码及测试验收、题目冻结、付费预算和实际答案裁决分别经过人工节点，当前进度见本文开头。
