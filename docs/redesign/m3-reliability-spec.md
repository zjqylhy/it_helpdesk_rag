## 1. 选择及范围

采用**评测进程共享的调度器 + 实验目录内独立持久调度状态**。现有 execution.lock 保证同一实验只由一个执行器推进；不引入 Redis、任务队列或新的编排框架。LangGraph 继续负责业务步骤，ModelSession 负责模型请求预算和调度接入，HTTP 适配器负责响应协议。

调度器不替代网关限流。网关仍负责多应用/多进程的统一准入；本批客户端调度仅协调当前实验，不能承诺其他应用占用额度时也绝不出现 429。API/Worker 的分布式全局配额不纳入本批；候选 API/Worker 继续关闭真实推理。429 识别和失败诊断供公共适配器复用。

持久调度状态与原实验账本分开：新实验目录保存 `scheduling.sqlite`，记录最近准入的路由、时间、预留估算以及冷却截止时间；原 `ledger.sqlite` 的调用与费用预算继续权威。取消或预算终止后的调度名额可以保守占用至窗口结束，不退款放大发送量；它不算已发模型 HTTP。旧报告无需迁移，旧目录禁止用新代码续跑。

## 2. 路由节流

本次只读复核网关 v31 的实际应用级单候选路由，得到如下配置。优先采用 80% 的客户端工作额度，保留共享服务余量；这只是下一次配置提案，不是已应用的网关变更。

| 路由 | 网关 RPM / TPM | 提议客户端 RPM / 估算单位每分钟 |
| --- | --- | --- |
| chat → deepseek-flash | 30 / 50000 | 24 / 40000 |
| embedding → qwen3.7-text-embedding | 24000 / 1000000 | 19200 / 800000 |
| rerank → qwen3.7-text-rerank | 3000 / 9000000 | 2400 / 7200000 |

通过冻结的 `rate-profile.json` 显式设置，不把当前服务器数值硬编码为所有环境的默认。profile 绑定配置版本、模型/提供方标识、端点指纹及估算算法版本；不含密钥。多个别名若指向同一上游配额，归入同一调度键。多候选或灰度路由未能解析配额归属时拒绝真实执行。

每个键使用 60 秒滑动窗口的请求数和预留单位，并设置 `60 / RPM` 最小发出间隔，避免窗口开始时突发。输出上限仍为 2048，不因节流调整。调度单位基于实际将发送的结构进行保守字节估算：包括模型消息框架余量与最大输出；重排将 Query 按文档数重复计入。该单位仍不冒充提供商 tokenizer 的硬 Token 保证，实际用量不反向释放本分钟预留。

准入顺序：校验权限与剩余请求预算 → 估算并检查单次是否超过窗口容量 → 等待路由槽位及冷却 → 再校验权限、deadline 和预算 → 请求账本落槽 → 发 HTTP。等待期间分段检查权限与取消，超过截止时间即以 `model_rate_deadline` 停止；不会为等限流额外延长 110 秒。

不同路由的等待互不阻塞；重试和后续题都复用该实例。重启后读取最近 60 秒准入和尚未到期冷却，不允许清空状态恢复突发。进程内采用单调时钟计算时限，跨进程记录 UTC；明显时钟回拨时停止，而不是提前释放窗口。

## 3. 429 与重试

| 情况 | 处理 |
| --- | --- |
| 429，合法 Retry-After | 识别非负秒数或 HTTP-date，保存其来源和等待值；设置该路由共享冷却 |
| 429，缺失或非法 Retry-After | 采用 60 秒保守冷却；记录 fallback，不快速连续请求 |
| 等待值超过本题剩余时间 | 不睡满后再发请求；保留本次已发请求，以限流/时限终止；冷却继续约束后续题 |
| 网络及可恢复 5xx | 仍最多一次重试，采用有界退避；调度、预算和 deadline 全部重新检查 |
| 非流式结构化/Embedding/Rerank | 每个业务调用最多两次 HTTP，包括第一次；重试没有额外预算池 |
| 流式生成 | 本批继续不自动重放；HTTP 429 或其他失败有独立诊断，已输出片段后尤其禁止重试 |

程序区分 `provider_rate_limited`、其他临时服务错误、调度超时、请求预算耗尽和实验预算耗尽，不把它们转换成资料不足拒答。保留状态码、规范化 Retry-After 和受限 request-id；不保存完整 header、认证信息或上游响应正文。成功与失败的已知用量均按实际可用字段保存。

Retry-After 的秒数/HTTP-date 语义依据 [RFC 9110 §10.2.3](https://www.rfc-editor.org/rfc/rfc9110.html#name-retry-after)。合法但超过本题时限的值不能截短后提前重试。共享服务可能仍拒绝请求，系统只保证按本地规则有界等待和停止。

## 4. 保留部分执行轨迹

GraphRunner 消费现有 `updates` 流，在每个节点完成时更新私有诊断：已完成节点、路由/必要库 ID、拆解状态、候选/融合/重排/上下文 ID 及原有哈希。节点调用处增加只写私有 observer 的进入/异常标记，以区分“已进入但失败”和“未执行”；不通过公开 custom 事件发送内部诊断。节点成功阶段以收到更新为准，返回后更新失败等不确定情形保留 unknown，不猜测已完成。只保存已发生的事实，不重新调用图或模型来补诊断，也不增加 LangGraph checkpointer。

评测入口无论成功还是失败都保存该快照；API 的受限 RunJournal 错误终态同样保存必要诊断。公开 SSE 不暴露这些内部字段、知识片段、提供方 request-id 或逐请求账本；公开耗时摘要与私有诊断分开，前端事件类型保持原契约。

阶段字段必须显式区分：

- `observed`：对应节点完成且有明确 ID 记录；可以基于冻结语料计算覆盖，空 ID 集合可真实得到 0。
- `not_reached`：失败或澄清/拒答提前结束，未执行该阶段；覆盖为 null。
- `failed`：该阶段已尝试但未完成；保留错误与可用的前序观测，不凭空补阶段输出。

例如当前图的 select_context 已完成、sufficiency 429：候选、融合、重排和上下文覆盖仍可计算，回答步骤尚未执行，不虚构其结果。拆解请求已尝试但失败时记录 attempted=true、accepted=null，不把它计为模型成功拒绝拆解。

实现依赖当前已锁定 LangGraph 的 `updates` 模式，不升级依赖；语义参照 [LangGraph 流式文档](https://docs.langchain.com/oss/python/langgraph/streaming)。失败仅保留有限的 IDs、哈希和状态，原问题、证据全文和未完成草稿不新增到诊断日志。进程被强制杀死前尚未写出的诊断仍可能丢失；持久请求槽保证这类运行不会自动重放。

## 5. 用量和报告

输入与输出独立判断已知性；报告同时列出已知小计、完整总量是否可得、未知次数和输出不适用次数。不得因某一路输出不适用而丢掉已知输入，也不得将失败请求未知值填为 0。

Embedding/Rerank 按输入计价，显式标识 `output_applicable=false`。若仅返回合法 total_tokens，只有在明确的输入模型语义下才可映射为输入量；Chat 只有 total_tokens 时不猜输入/输出分摊。保留原始缺失状态及字段来源，内部归一化的输出零和供应商测得的输出零需可区分。

现有成功/失败分母、完整运行比例、每阶段覆盖观测数、拆解实际尝试数/接受数、状态分层 P95、TTFT 样本数和排队耗时分别报告。只有两个策略都观测到同一阶段的题才形成对应阶段的成对差值；不能把服务失败算作召回为零，也不能只展示成功子集的 100%。

首版离线费用汇总修正应进入正式报告路径，并标出价格版本和未计价记录；供应商实际账单与估算继续分开。原批次只保留此前 v2 修订，不由新工具覆盖重写。

## 6. 冻结及代码边界

拟修改位置：`application/model_session.py`、模型适配器与用量结构、`graph/baseline.py` 的诊断收集、`entrypoints/evaluate.py` 与评测汇总、HTTP 错误终态的私有 RunJournal；新增独立的调度模块及端口。优先复用现有 SQLite 和权限 guard，不修改检索节点决策或提示，不为本次修复引入业务库迁移。

| 验收 | 必须覆盖的场景 |

| 调度 | 跨题/跨策略共享；RPM/估算窗口；最小间隔；不同路由独立；超大单次拒绝；取消、权限变更、等待时限 |

| Retry-After | 秒数、HTTP-date、过去日期、缺失、非法/超大值；等待不足时只保留原调用；后续题遵守冷却 |
| HTTP 与流 | 429/5xx/网络错误区分；最多一次非流式重试；所有请求先落账；生成不重放、断连关闭上游 |
